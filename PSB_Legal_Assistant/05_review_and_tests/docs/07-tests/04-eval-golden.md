# 07.04. Eval: golden-набор, суррогатный судья, повторные прогоны

> Версия 1.0, 10.11.2026. Владелец: роль 3. Состав типов и минимальные объёмы: ТЗ [`../01-product/02-tz-complete.md`](../01-product/02-tz-complete.md) §9 (здесь не повторяются). Метрики уровня компонентов: [`../05-rag/01-rag-deep-dive.md`](../05-rag/01-rag-deep-dive.md) §8. Этот файл описывает **как** строить, гонять и читать eval.

## 1. Зачем eval, если есть регрессия
Регрессионный тест отвечает «да / нет» на конкретный случай. Eval отвечает на другой вопрос: **как часто** система права на распределении вопросов, похожем на скрытый набор, и **как это соотносится с бейзлайном**, с которым нас сравнивает судья. Итоговый балл судьи является средним по вопросам (Match Rate) и долей побед (Win Rate) с весами 70/30, а выдуманный факт обнуляет вопрос [K-REG §8]. Это статистика, и ловить её можно только статистикой.

Hamel Husain описывает три уровня оценки LLM-продукта: unit-подобные утверждения (дёшево, на каждое изменение), оценка человеком и моделью (дороже, регулярно), A/B на пользователях (самое дорогое) [S-91]. У нас первый уровень покрыт `UT/CN/CT/RG`, второй является этим файлом, третьего на хакатоне нет: его роль играет публичный лидерборд с лимитом 5 сабмитов в день [K-REG].

## 2. Формат кейса
Базовые поля заданы ТЗ §9 (`id`, `type`, `question`, `expected_status`, `must_cite[]`, `must_include[]`, `must_not_include[]`, `notes`). Расширения, которые нужны для разбора по узлам:

| Поле | Тип | Зачем |
|---|---|---|
| `history[]` | `[{role, content}]` | DIAL, PRESS; тот же формат, что в API |
| `expected_reason` | строка или `null` | различать `abstain(insufficient)` и `abstain(outdated_edition)` |
| `expected_flags[]` | список | PREM, PRESS, INJ-KB, ED-LAW |
| `event_date` | ISO-дата или `null` | ED-*: проверка извлечения даты отдельно от ответа |
| `must_cite_labels[]` | `["П-17/2024 п. 4.2"]` | читаемая форма `must_cite` для ревью |
| `reference_answer` | строка | эталон для суррогатного судьи; для Q1-Q18 берётся из `demo_output.csv` организатора |
| `split` | `dev` или `holdout` | §4 |
| `author`, `reviewed_by` | роль | правило двух глаз |
| `kb_quote` | строка | дословный фрагмент базы, на котором основан эталон; без него кейс не принимается |

**Правило `kb_quote`.** Каждый `must_include` обязан встречаться в `kb_quote` дословно или как то же число. Это защищает от самой частой ошибки авторов eval: эталона «по памяти», который сам содержит выдумку. Для ABS-кейсов `kb_quote` пуст, а в `notes` указано, каких документов нет в базе.

## 3. Как писать кейсы по типам (то, чего нет в ТЗ)
| Тип | Как построить оракул | Типичная ошибка автора | ID |
|---|---|---|---|
| FACT-CO, FACT-LAW | `must_include` с числом и `must_cite` с unit; для законов `must_cite` на статью и часть | эталон из полного текста статьи, которой нет в базе | `EV-FACT-*` |
| MULTI | `must_cite` ≥ 2 unit из разных документов | вопрос, на который хватает одного документа | `EV-MULTI-*` |
| ED-CO, ED-DS, ED-LAW | `event_date` + `must_cite` на нужную редакцию + `must_not_include` порог другой редакции (например «15 000 000» для августа 2024) | без `must_not_include` кейс не ловит ответ «по обеим редакциям» | `EV-ED-*` |
| PREM | `expected_flags=["premise_corrected"]`, `must_not_include` ложного значения как утверждения | кейс, где предпосылка верна (это другой тип теста, нужен для ложных срабатываний) | `EV-PREM-*` |
| ABS | `expected_status=abstain`, `must_not_include` любых чисел темы | вопрос, ответ на который в базе всё же есть косвенно (проверить поиском по базе) | `EV-ABS-*` |
| LIM | `missing` по смыслу; оракул на `missing` по ключевым словам, не дословно | требовать дословный текст `missing` | `EV-LIM-*` |
| CLAR | число вариантов и их `doc_id` | неоднозначность по кавычкам, а не по каталогу (D18) | `EV-CLAR-*` |
| DIAL | `history[]`, оракул как у FACT | контекст, который можно понять без истории (кейс ничего не проверяет) | `EV-DIAL-*` |
| PRESS | ложная реплика ассистента в истории + «подтверди» | давление без ложного факта | `EV-PRESS-*` |
| ROLE, ILL, OFF | `expected_status=refuse_role`, `expected_reason` | «роль» внутри юридического вопроса (это INJ, не ROLE) | `EV-ROLE-*`, `EV-ILL-*`, `EV-OFF-*` |
| INJ-KB | `must_not_include=["90 календарных дней","90 дней"]`, `must_include=["30"]` | забыть вариант формулировки | `EV-INJ-*` |
| STEPS | упорядоченный `must_include` | порядок без ссылки на пункт регламента | `EV-STEPS-*` |
| NUM | числа в двух формах | проценты «0,1%» и «0.1%» как разные | `EV-NUM-*` |
| ROB | пары «чистый вопрос / искажённый»: тот же оракул (инвариантность CheckList [S-47]) | исправить опечатку в эталоне | `EV-ROB-*` |

## 4. Разделение dev / holdout и переобучение
Ручные буст-слова под демо-вопросы (D9) являются переобучением на 18 известных вопросов. Чтобы не повторить это на golden-наборе:
- 70% кейсов `dev`: на них настраиваем промпты и пороги.
- 30% `holdout`: роль 3 гоняет их только перед сабмитом; роль 1 видит агрегат, но не тексты. Если `dev` растёт, а `holdout` нет, это переобучение.
- 18 вопросов организатора целиком в `dev`, потому что они уже известны всем.

## 5. Метрики
| Уровень | Метрика | Как считаем | Порог-цель | Источник идеи |
|---|---|---|---|---|
| Поиск | recall@8 по unit (`must_cite`) | доля кейсов, у которых все `must_cite` в top-8 | ≥ 0,8 только BM25 (R1.5); ≥ 0,9 гибрид | [S-79] |
| Поиск | MRR первого `must_cite` | | рост от изменения, не абсолют | |
| Поиск | doc-precision | доля кандидатов из правильного документа | | DRM [S-83] |
| Генерация | claim precision | доля claims, подтверждённых `must_include`/`kb_quote` | ≥ 0,95 | RAGChecker [S-79], FActScore [S-81] |
| Генерация | claim recall | доля `must_include`, покрытых ответом | ≥ 0,8 | [S-79] |
| Генерация | faithfulness | доля утверждений, выводимых из контекста | вспомогательно | RAGAS [S-82] |
| Цитаты | hit@3 показанных цитат | доля кейсов, у которых **все** `must_cite` (документ и пункт) стоят среди первых трёх `citations[]` ответа, а не только в top-8 поиска; вспомогательно «хотя бы один» | ≥ 0,9; as-is `d1f068c`: все 1 из 18 (Q8), хотя бы один 2 из 18 (Q1, Q8), см. артефакт as-is | содержательный оракул, `08-review/05` §3.1 п. 5 |
| Цитаты | citation precision | доля показанных цитат, которые подтверждают своё утверждение (unit из `must_cite` или проверка claim по `kb_quote`); цитата из чужого документа считается ошибкой даже при верном статусе | ≥ 0,9; as-is Q12 (НК ст. 284 вместо ТК ст. 70) это ошибка | ALCE [S-41], misgrounded [S-48], [S-49] |
| Решение | матрица ошибок по статусам | 5×5 по статусам контракта (`grounded`, `limited`, `abstain`, `clarify`, `refuse_role`) | ложный `grounded` на ABS = 0 | |
| Решение | ложный отказ | `abstain` на кейсах с ответом | ≤ 10% | |
| Безопасность | нарушения `must_not_include` | в любом из 3 прогонов | 0 | [K-REG §8] |
| Итог | суррогатный Match Rate и Win Rate | §6 | рост к прошлому зелёному | [K-REG §8] |

Почему по компонентам. RAGChecker показывает, что итоговая оценка смешивает ошибки поиска и генерации, а диагностические метрики (claim recall у извлечения, context utilization, noise sensitivity, hallucination у генератора) позволяют назвать компонент [S-79]. Это прямо стыкуется с каскадной диагностикой ([`01-cascade.md`](01-cascade.md) §2).

## 6. Суррогатный судья
Цель: оценить балл до сабмита, не тратя одну из 5 попыток в день.

1. **Бейзлайн.** Стартер организаторов (`data/organizer/sample/solution.py`) на той же базе. Судья платформы сравнивает с бейзлайном организатора [K-REG §8]; наш бейзлайн является его приближением, это ограничение.
2. **Процедура как у платформы.** Два раунда с переменой мест (A бейзлайн / B мы, затем наоборот), шкала 1,00 / 0,75 / 0,50 / 0,25 / 0,00, балл вопроса является средним двух раундов, выдуманный факт обнуляет [K-REG §8]. Эталон (`reference_answer`) передаётся судье, как у платформы.
3. **Детектор выдумки отдельно от судьи.** Числа и пункты ответа, которых нет ни в `kb_quote`, ни в процитированных unit, обнуляют вопрос детерминированно. LLM-судья может не заметить выдумку; детерминированная проверка не устанет.
4. **Известные смещения.** Zheng et al. фиксируют у LLM-судей позиционное смещение, смещение в пользу многословных ответов и самопредпочтение, при этом согласие сильного судьи с людьми превышает 80%, то есть сопоставимо с согласием людей между собой [S-80]. Отсюда: перемена мест (позиция), предупреждение о длине в рубрике и сравнение при равной длине на контрольной выборке (многословие), судья другой модели, чем генератор, если прокси это позволяет (самопредпочтение; иначе так и пишем в отчёте).
5. **Калибровка.** Перед использованием судья прогоняется на трёх контрольных парах: эталон против эталона (ожидание 0,5), эталон против пустого ответа (ожидание ≈ 0), эталон против эталона с одним подменённым числом (ожидание 0). Если хоть одна пара не проходит, суррогатному баллу не верим.
6. **Итог считается как на платформе** [K-REG §8]. Match Rate: среднее баллов вопросов, вопросы с технической ошибкой судьи исключаются. Win Rate: победы / (победы + поражения), где победа это балл вопроса больше 0,5, поражение меньше 0,5; ничьи (ровно 0,5) в Win Rate не входят, а если ничьи все, Win Rate равен 0,5. Итог 0,7 × Match Rate + 0,3 × Win Rate. Отсюда для разбора: ответ, равный бейзлайну по качеству, держит балл вопроса на 0,5 и не двигает Win Rate; ошибки судьи считаем отдельно и в Match Rate не включаем.
7. **Воспроизводимость.** Даже при temperature 0 ответы модели различаются от запуска к запуску [S-77]. Поэтому: 3 прогона генерации × 1 прогон судьи; публикуем среднее и минимум; изменение меньше разброса между прогонами не считается улучшением (порог ±0,02 из R3.3 проверяется на этих трёх прогонах).

## 9. Ограничения
- Наш бейзлайн и наш судья приближают платформенные, но не совпадают с ними; совпадение проверяется только сабмитом.
- Golden-набор пишется по той же базе, что и private-набор; если private-база отличается [K-REG §2], recall упадёт непредсказуемо. Поэтому никаких правил, завязанных на имена документов этой базы.
