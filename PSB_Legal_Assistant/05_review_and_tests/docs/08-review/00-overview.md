## 1. Зачем ревью в команде из трёх человек
Ревью кажется роскошью, когда людей трое и до дедлайна неделя. Но у нас две причины, по которым без него хуже:
1. **Цена ошибки несимметрична.** Выдуманный факт обнуляет вопрос у судьи [K-REG §8], сабмит с нулём означает недопуск к экспертам [K-PDF]. Ошибки этого класса дешевле поймать глазами второго человека, чем лидербордом с лимитом 5 попыток в день.
2. **Командное владение оценивается** (5% финала [K-PDF]): ревью является основным способом, которым роль 2 узнаёт, как устроен ND6, а роль 1 узнаёт, почему в UI нет «печатающих точек».

Что о ревью известно из практики. Исследование ревью в Google (9 млн изменений) показало, что изменения в основном маленькие (медиана 24 строки), у большинства один ревьюер, первый отклик на малые изменения приходит меньше чем за час, а главные мотивы ревью: обучение, поддержание норм, контроль качества и предотвращение случайных ошибок; поиск дефектов является лишь одной из целей [S-123]. Стандарт ревью Google формулирует критерий одобрения: изменение **улучшает общее состояние кода**, даже если не идеально; «идеального кода не бывает» [S-118]. Это критерий, а не лозунг: ревьюер не блокирует PR ради своего вкуса, но блокирует то, что ухудшает систему.

Исследование ревью в Microsoft (873 разработчика, 165 менеджеров, 570 размеченных комментариев) даёт два вывода, важных для нас [S-137]. Первый: поиск дефектов остаётся главным ожидаемым мотивом (первым его назвали 44% разработчиков), но комментариев про дефекты мало, и они в основном о мелких логических ошибках. Отсюда правило пакета: P0-дефекты вроде D22 (одно исключение обрывает CSV) ловит тест `RG-DEF-D22`, а не внимательность ревьюера. Второй: главное в ревью понимание контекста изменения. Поэтому описание PR (§3.4, шаблон в [`01-code-review-core.md`](01-code-review-core.md)) обязательно называет узел ND, дефект D и тесты: без них второй человек видит diff, но не видит, что именно должно было измениться.

## 2. Виды ревью
| Вид | Предмет | Кто проводит | Когда | Блокирует |
|---|---|---|---|---|
| Код ядра | PR в `psb_*.py`, `solution.py`, `server.py`, промпты, контракт | роль 1 автор; ревьюер роль 3 (поведение, данные), роль 2 при изменении контракта | каждый PR в `main` | слияние |
| Фронт и дизайн | PR в `apps/web`, токены, тексты | роль 2 автор; ревьюер роль 1 (контракт) и роль 3 (тексты, сценарии) | каждый PR в `apps/web` | слияние |
| Архитектурное | ADR, новые узлы, изменение границ, fail-closed | автор ADR; ревьюеры две другие роли | до начала реализации | старт работы |
| Безопасность | секреты, инъекции, роль, CORS, логи | роль 1 + роль 3 по чеклисту угроз | PR с метками `security`, `prompt`, `contract`; перед каждым сабмитом и перед финалом | слияние, сабмит |
| Тесты и eval | новые тесты, оракулы, golden, отчёты | роль 3 для тестов роли 1 и 2; роль 1 для golden роли 3 | каждый PR с тестами; каждый отчёт перед сабмитом | слияние, сабмит |
| Документация | README, ADR, этот пакет, презентация | роль 3 автор; ревьюеры роль 1 (соответствие коду), роль 2 (UI) | при изменении поведения; перед дедлайном | релиз |

## 3. Общие правила для всех видов
### 3.1. Размер и скорость
- Маленькие изменения: Google считает 100 строк обычно разумным размером, 1000 обычно слишком большим [S-121]. Наш ориентир: до ~400 изменённых строк кода на PR, кроме механических переносов (R1.1), которые помечаются `refactor-only` и ревьюятся на «поведение не изменилось».
- Отклик: Google просит отвечать максимум в течение одного рабочего дня [S-120]. Наш ритм короче: PR, открытый до 18:00 мск, получает первый отклик в тот же день, иначе он блокирует вечернее окно сабмитов (03 §7).
- Почему не больше: данные вендора SmartBear/Cisco про 200-400 строк за 60-90 минут часто цитируются, но это вендорское исследование, вес у него низкий [S-130]; мы опираемся на него только как на согласующееся с Google наблюдение.

### 3.2. Метки комментариев
Каждый комментарий начинается с метки, чтобы автор понимал, что обязательно:

| Метка | Значение | Блокирует |
|---|---|---|
| `blocking:` | нарушает инвариант, контракт, безопасность, брендовый запрет или требование кейса | да |
| `issue:` | дефект, но можно исправить следующим PR, если заведён D-номер или задача | по согласованию |
| `question:` | ревьюер не понимает; ответ должен попасть в код (комментарий, имя) или в PR | нет |
| `nit:` | мелочь, стиль | нет |
| `fyi:` | контекст | нет |

Метки Nit / Optional / FYI предлагает Google [S-122], разделение blocking / non-blocking описывает Conventional Comments [S-135]. Google также просит комментировать код, а не автора [S-122].

### 3.3. Как фиксировать находку
Находка, которую не исправили в этом PR, обязательно становится одним из:
- D-номером в таблице [`../05-rag/01-rag-deep-dive.md`](../05-rag/01-rag-deep-dive.md) §7 + тестом `RG-DEF-Dn` (`xfail`) в [`../07-tests/02-regression.md`](../07-tests/02-regression.md);
- задачей с R-номером, если это недостающая функция;
- записью «риск принят» в `DECISIONS.md` с причиной и датой.
Комментарий в закрытом PR не является фиксацией: его никто не найдёт.

Формат записи находки (в PR или в отчёте ревью):
```
[вид ревью] [blocking|issue|question|nit] <узел или файл:строки>
Что: одно предложение.
Почему важно: какой инвариант, требование или критерий.
Как проверить: тест или шаг воспроизведения.
Предложение: (необязательно).
```

### 3.4. Готово / не готово к слиянию (общее для всех видов)
Готово:
- нет открытых `blocking:`;
- CI зелёный по слоям из [`../07-tests/00-strategy.md`](../07-tests/00-strategy.md) §4;
- каждый `issue:` закрыт или превращён в D / R / риск;
- описание PR говорит «что», «зачем», «как проверено», ссылки на R-, D-, ND-номера.

Не готово:
- «поправлю потом» без номера;
- изменённое поведение без теста;
- PR смешивает рефакторинг и изменение поведения.

### 3.5. Ревью после слияния
LLVM допускает ревью после коммита для доверенных авторов с откатом при проблемах [S-125]. Мы используем это только для документации и `nit`-исправлений в последний день; код ядра и контракт ревьюятся до слияния.

## 4. Частые ошибки ревьюера (общие)
| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Смотреть только diff | инварианты нарушаются в соседнем, неизменённом коде (например, рендер дописывает «Источники» после проверки) | открыть узел целиком, сверить с файлом узла в `06-nodes` |
| Блокировать за вкус | замедляет без пользы; Google: одобрять, если код улучшает систему [S-118] | `nit:` и одобрение |
| Одобрять без запуска | тесты могут проходить из-за слабых оракулов (D28) | для поведенческих PR прогнать хотя бы один RG-кейс руками |
| Принимать «тест есть» | тест с `in {a, b}` ничего не проверяет | читать оракул ([`05-tests-and-eval-review.md`](05-tests-and-eval-review.md)) |
| Ревью держит PR сутки | вечернее окно сабмитов сгорает | первый отклик в тот же день [S-120] |
| Не фиксировать находку | дефект возвращается | §3.3 |

## 5. Метрики ревью (без бюрократии)
Считаем только то, что помогает: время до первого отклика, число PR больше 400 строк, число находок `blocking`, ставших D-номером. Ничего не считаем «на человека».
