# 08.01. Ревью кода ядра: RAG, проверка, `solution.py`, контракт API

> Версия 1.0, 10.11.2026. Общие правила (метки, фиксация, готовность): [`00-overview.md`](00-overview.md). Узлы ND1-ND7: [`../06-nodes/`](../06-nodes/). As-is примеры взяты с `d1f068c`.

## 1. Зачем и кто
**Зачем.** Ядро решает, что пользователь и судья получат как факт. Ошибка в ядре не выглядит как ошибка: ответ приходит, статус `grounded`, цитата есть, только неверная. Поэтому ревью ядра ищет прежде всего **нарушения инвариантов fail-closed**, а не стиль.

**Кто.**
| PR | Автор | Обязательный ревьюер | Почему он |
|---|---|---|---|
| ND1-ND6, промпты | роль 1 | роль 3 | знает базу и golden; видит, когда изменение «подгоняет» под известные вопросы |
| Контракт `AnswerV2`, API, SSE | роль 1 | роль 2 **и** роль 3 | потребители контракта |
| `solution.py`, сборка, `requirements.txt` | роль 1 (или роль 2 по 03 §9) | роль 3 | ведёт журнал сабмитов, отвечает за смоук |
| Изменение порогов, `PROMPT_VERSION`, `PSB_RERANK` | роль 1 | роль 3 + отчёт eval | такие изменения влияют на судью сильнее кода (03 §7) |

Chromium решает ту же задачу файлами OWNERS: у каждого каталога есть люди, без одобрения которых изменение не принимается [S-124]. У нас «владелец» задан таблицей выше и RACI в [`../01-product/07-handoffs-and-interfaces.md`](../01-product/07-handoffs-and-interfaces.md) §4.

## 2. Когда
- Каждый PR в `main` до слияния. Первый отклик в тот же рабочий день [S-120].
- Отдельно: PR, меняющий промпт или пороги, ревьюится **вместе с отчётом eval** по затронутым типам; без отчёта не смотрим.
- Перед каждым сабмитом: короткое ревью diff от прошлого сабмита (`git diff <прошлый sha>..HEAD -- '*.py' requirements.txt`), чтобы понимать, что именно проверяет сабмит.

## 3. Что приносит автор
Описание PR по шаблону:
```
Что: …
Зачем: R-номер / D-номер / ND-узел.
Как проверено: какие UT/CN/CT/RG/EV; для поведенческих изменений: до/после на конкретных вопросах.
Риски: что может сломаться и где.
Тип: refactor-only | behavior | contract | prompt | config
```
`refactor-only` означает: поведение не меняется, и ревьюер проверяет именно это (те же ответы на as-is прогоне). Смешение рефакторинга и поведения в одном PR является причиной вернуть PR без ревью: в смешанном diff невозможно увидеть, что изменило поведение.

## 4. Как смотреть: порядок
Google советует начинать с общего дизайна изменения и описания, затем смотреть главную часть, затем остальное [S-119]. Наш порядок:
1. **Описание и тип.** Понятно ли, что меняется и зачем; соответствует ли тип diff-у.
2. **Тесты.** До кода. Если оракул слабый, ревью кода бессмысленно ([`05-tests-and-eval-review.md`](05-tests-and-eval-review.md)).
3. **Инварианты затронутого узла.** Открыть файл узла в `06-nodes`, раздел «Инварианты», пройти по каждому.
4. **Код.** Логика, крайние случаи, ошибки, конфиг.
5. **Запуск.** Для `behavior` и `prompt`: прогнать руками 2-3 RG-кейса, указанных в описании.

## 5. Что смотреть по узлам
Ниже не чеклист, а то, **почему** конкретное место опасно и как это увидеть в diff.

### 5.1. ND1 ингест
- **Офсеты.** Любая нормализация (NFKC, `ё`, пробелы) применяется к копии для поиска, а не к `text`, из которого берётся цитата. Признак ошибки в diff: `text = normalize(text)`. Проверка: CT-B1-03.
- **Метки.** Метка пункта берётся из начала строки по шаблону нумерации, а не из «первого числа». As-is `_chunk_text` (pipeline.py 101-128) даёт метки-даты (D5): любое возвращение к «первому числу» блокируется.
- **Заголовок.** Не из имени файла: as-is pipeline.py 135 вставляет в заголовок U+2014 и номер «А-08-2024» вместо «А-08/2024» (D24).
- **Санитайзер.** Помеченный абзац не в индексе, но в просмотре документа. Признак ошибки: фильтр применён до записи `units.jsonl` (тогда UI не сможет показать документ целиком).

### 5.2. ND2 поиск
- **Нет правил под известные вопросы.** Любой список слов, совпадающих с демо-вопросами («меридиан», «северн», «альфа»), является переобучением (D9, pipeline.py 182-204). Ревьюер роль 3 именно поэтому: он знает формулировки 18 вопросов и узнает их в коде.
- **Одна токенизация для индекса и запроса.** Две функции `tokens` в разных местах являются будущим расхождением.
- **Пороги гейта из конфигурации**, с отчётом eval при изменении.

### 5.3. ND3 вход и гарды
- **Лимит 4000** в Pydantic (`max_length` [S-99]), а не ручной `len()` в обработчике.
- **История доходит** (as-is server.py 55 её теряет, D19).
- **Гард не отказывает юридическому вопросу** со словом «система» или «инструкция» (UT-GRD-05). Ложный отказ хуже пропуска: бейзлайн отвечает.

### 5.4. ND4 каталог и `clarify`
- **Сопоставление по точному равенству основ**, не по префиксу («трейд» является префиксом «трейдинг», UT-CAT-03).
- **Нет имён из базы в коде.** As-is `_DEMO_ENTITY_FRAGMENTS` (pipeline.py 251-260) является списком фрагментов имён; to-be каталог строится из преамбул.

### 5.5. ND5 редакции
- **Строгие неравенства** («свыше 3 млн» → `>`), граница дат включительно/исключительно по тексту базы, тест на каждую границу (UT-ED-01, 02, 05, 07).
- **Редакцию выбирает код**, не модель.

### 5.6. ND6 генерация, проверка, решение
Самое важное место ревью.
- **Проверка не тавтологична.** Код не должен добавлять в ответ то, что потом проверяет. As-is pipeline.py 410-415 дописывает «Источники: …», а 420-425 проверяет их наличие (D7). Любой код вида «если не нашли, добавим и проверим снова» блокируется.
- **Статус является функцией сигналов.** Если в diff появляется `status = llm_output["status"]` без матрицы, это `blocking`.
- **Контекст полный.** As-is `quote[:240]` (pipeline.py 394-402): п. 4.2 П-17/2024 (срок оплаты 30 дней) стоит в чанке на позиции 483 и в контекст не попадает (D1). Любое усечение контекста требует теста, что нужный факт остаётся.
- **Числа.** Каждое число ответа есть в процитированном unit (UT-VER-04, 05).
- **Repair не больше одного**, с перечнем проваленных проверок.

### 5.7. ND7 API и сабмит
- **Батч переживает исключение** (as-is solution.py 50-66 без try/except, D22). Отдельно смотреть, где открывается выходной файл: as-is `open("w")` в строке 59 до первого ответа затирает прежний `submission.csv`; в PR файл пишется во временный и переименовывается, а проверка базы и `questions.csv` стоит до этого (ND7 §3.2 п. 8, RG-SUB-09). Признак ошибки: `except Exception: pass` без строки в stderr и без счётчика запасных ответов.
- **Атомарная запись** (`os.replace` [S-97]), `QUOTE_ALL` (as-is строка 60 есть [S-98]).
- **`DATA_DIR` по умолчанию `data`** [K-REG]; as-is default `data/organizer/tests` (95-99).
- **Без аргументов пишет CSV** (as-is exit 2, 102-107, D2).
- **Нет импорта из `apps/`** (D3).
- **Версии `==`** (D17) и только разрешённые пакеты [K-REQ].

### 5.8. Промпты
Промпт является кодом. Ревью промпта:
- версия `PROMPT_VERSION` выросла;
- отчёт eval по типам, которые промпт затрагивает (минимум INJ-KB, PRESS, ROLE и тип, ради которого изменение);
- промпт не содержит фактов базы («срок оплаты 30 дней»): это подсказка модели, которая на private-базе станет выдумкой;
- инструкции об источниках: «только из контекста», формат JSON claims; нет «если не знаешь, ответь по общим знаниям».

### 5.9. Конфигурация и окружение
Конфигурация из окружения, а не в коде (12-factor [S-90]). As-is `_call_llm` игнорирует `LLM_TEMPERATURE`/`LLM_MAX_TOKENS` (pipeline.py 334-335, D26): ревьюер проверяет, что каждая переменная из `.env.example` реально читается, и наоборот.

## 6. Ревью изменения контракта
Отдельная процедура, потому что ломает двух потребителей:
1. Схема, фикстуры и провайдерские тесты в одном PR ([`../01-product/07-handoffs-and-interfaces.md`](../01-product/07-handoffs-and-interfaces.md) §3).
2. Роль 2 подтверждает: «фикстуры рендерятся», роль 3: «eval читает новое поле».
3. Несовместимое изменение без роста `schema_version` блокируется.
4. Новое значение статуса или `reason` требует строки в матрице S17 и теста UT-DEC.

## 7. На что влияет находка
| Класс находки | Пример | Уровень | Влияет на |
|---|---|---|---|
| Сабмит может не создаться | импорт из `apps/`, нет default `DATA_DIR` | `blocking` | допуск [K-PDF] |
| Путь к выдумке | тавтологичная проверка, статус от модели, факт в промпте | `blocking` | обнуление у судьи [K-REG §8]; Достоверность 25% |
| Неверная редакция или контрагент | граница дат, префиксное сопоставление | `blocking` | судья; Архитектура 20% |
| Ложный отказ | слишком строгий гард | `issue` (если тест есть) | Match Rate |
| Скорость | лишний вызов LLM | `issue` | Скорость 15% |
| Стиль | имена | `nit` | нет |

## 8. Как зафиксировать
По [`00-overview.md`](00-overview.md) §3.3: D-номер + `RG-DEF-Dn` или R-задача или «риск принят». Для находок по as-is коду при первом ревью этого прохода так и сделано: D19-D28 добавлены в 05-rag/01 §7 с тестами.

## 9. Готово / не готово
Готово к слиянию:
- инварианты затронутых узлов проверены (п. 4.3);
- тесты: новый код покрыт UT; поведение покрыто RG или EV; дефект закрыт снятием `xfail`;
- для `prompt`/`config`: отчёт eval без жёсткой регрессии ([`../07-tests/00-strategy.md`](../07-tests/00-strategy.md) §5);
- RG-SUB-01 зелёный, если тронуты `solution.py`, сборка или зависимости.

Не готово:
- `grounded` возможен без проверенной цитаты;
- новый порог без eval;
- PR > 400 строк поведения;
- смешение `refactor-only` и `behavior`.

## 10. Частые ошибки ревьюера ядра
| Ошибка | Пример из as-is | Как избежать |
|---|---|---|
| Доверять зелёным тестам | `test_organizer_maternity_abstain` принимает и `abstain`, и `grounded` (D28) | читать оракул до кода |
| Смотреть только diff | рендер в 410-415 не в diff, но ломает проверку в 420-425 | открыть функцию целиком |
| Не узнавать подгонку | `boost_terms` под демо-вопросы (D9) | ревьюер роль 3 знает вопросы |
| Не запускать | as-is на 17 из 18 вопросов `grounded`, но все нужные пункты среди меток первых трёх цитат только у Q8 (Q1 частично) | прогнать 2-3 RG-кейса |
| Пропускать конфиг | `.env.example` задаёт `HTTP_ADDR=:8090` (строка 11), ядро тоже 8090 | сверить переменные с кодом |
| Принимать «потом» | | §8 |

## 11. Почему так
- Критерий одобрения «улучшает систему» и скорость отклика: Google [S-118], [S-120].
- Порядок «дизайн → главное → остальное»: Google [S-119].
- Малые изменения: Google [S-121]; эмпирика размеров: Sadowski et al. [S-123].
- Владельцы каталогов: Chromium OWNERS [S-124].
- Ручной разбор опасных мест и ревью по diff с контекстом: OWASP Secure Code Review [S-126], [S-127].
- Политики ветки (обязательные ревьюеры и проверки перед слиянием): Azure DevOps [S-129]; практики ревью: Microsoft ISE Playbook [S-128].
