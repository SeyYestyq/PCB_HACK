## R1.8. Понимание вопроса, история, каталог контрагентов, `clarify`

**Узел:** ND3, ND4. **Влияет на:** судья; Интерфейс 15% (кнопки вариантов). **Зависит от:** R1.3, R1.5.

**Зачем и почему именно так.** D18 на `d1f068c`: «Гарантия по договору с «Альфой»?» получает `grounded` по П-17/2024, хотя «Альфа» подходит к двум контрагентам; без кавычек тот же вопрос получает голое `clarify`. Неоднозначность определяется по кавычкам, а не по базе. Один уточняющий вопрос заметно повышает качество выдачи (в эксперименте Aliannejadi et al. более 170% по P@1 [S-84]), но лишнее уточнение раздражает; бенчмарк CLAMBER показывает, что LLM плохо распознают, когда уточнять [S-85]. Поэтому решение принимает код по каталогу, а не модель.

**Вход.** `Turn[]`, каталог контрагентов (ND4).

**Выход.** `standalone_question`, сущности из каталога, `clarify.options[]` с проверенной цитатой у каждого варианта.

**Шаги.**
1. Каталог из преамбул: карточка на сторону, основы Snowball, ИНН, номера, связанные ДС.
2. Сопоставление упоминания с карточками: **точное равенство основ** («трейд» ≠ «трейдинг»), номер договора и ИНН однозначны сами по себе; правовая форма «ООО» и кавычки ничего не сужают (оба кандидата ООО, ND4 §4 п. 6 [S-148], [S-149]).
3. ≥ 2 карточки и нет различающего признака в истории → `clarify` с вариантами; 1 карточка → поиск с фильтром; 0 → общий поиск.
4. S7 (LLM) переписывает follow-up в самостоятельный вопрос; сущности проверяются по каталогу (CT-B7-01).

**Готово, если:**
- RG-DEF-D18: `clarify` с 2 вариантами; RG-ST-CLAR-03: нет `clarify` на «Альфа-Трейд»; RG-HIS-04: после выбора в истории ответ по ПТ-05/2023 п. 6.1; RG-ROB-03: кавычки не меняют исход.

**Не готово, если:**
- Решение по кавычкам или по списку демо-фрагментов (`_DEMO_ENTITY_FRAGMENTS`, pipeline.py 251-260).
- Сопоставление по префиксу.

**Тесты:** UT-DLG-*, UT-CAT-*, UT-QU-*, CT-B4-*, CT-B6-*, CT-B7-*, CT-B9-03, CT-B11-05, RG-DEF-D11, RG-DEF-D18, RG-ST-CLAR-*, RG-HIS-04, EV-CLAR-*, EV-DIAL-*.

**Риск и что делать:** на private другие контрагенты: каталог строится из базы, без захардкоженных имён.

## R1.12. Деградация L0-L4, атомарный CSV, таймауты

**Узел:** ND6, ND7. **Влияет на:** Работоспособность 20%; допуск. **Зависит от:** R1.9.

**Зачем и почему именно так.** As-is цикл `run_batch` (solution.py 50-66) без try/except: исключение на одном вопросе обрывает файл (D22), в нём остаются заголовок и строки до сбойного вопроса, а прежний `submission.csv` уже обнулён открытием на запись (строка 59); у LLM нет повторов, `TEMPERATURE`/`MAX_TOKENS` из окружения не читаются (D26). Каскадные отказы растут через бесконтрольные повторы [S-87]; регламент требует ограниченных повторов на 429/5xx [K-REG §9].

**Вход.** вопросы, бюджет 20 минут [K-REG §5].

**Выход.** полный CSV при любом состоянии прокси.

**Шаги.**
1. Политика повторов: ≤ 3 попытки, экспонента с jitter [S-88], без повторов на 401.
2. Таймаут на вызов и на вопрос; дедлайн всего прогона с понижением уровня.
3. Исключение на вопросе → L4-ответ для этой строки, ID и тип исключения в stderr, счётчик запасных ответов в конце (ND7 §3.2 п. 8, [S-145]).
4. Системные отказы (нет вопросов, база не читается) проверяются до открытия выходного файла: ошибка и код выхода не 0, старый файл цел.
5. Запись во временный файл и `os.replace` [S-97].

**Готово, если:**
- CT-B14-*, RG-DEG-*, RG-SUB-05, RG-SUB-07, RG-SUB-09, RG-DEF-D22, RG-DEF-D26.

**Не готово, если:**
- Пустые ячейки при сбое.

**Тесты:** UT-CSV-*, CT-B14-*, RG-DEG-*, RG-SUB-*, RG-DEF-D22, RG-DEF-D26.

**Риск и что делать:** L4 даёт слабые ответы; но непустой ответ лучше нуля.
