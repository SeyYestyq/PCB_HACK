## 1. Место в потоке
ND4 стоит дважды. **До поиска** (S7) он превращает вопрос и историю в самостоятельный запрос и список сущностей. **После фильтров ND5** он решает, есть ли неоднозначность, которая меняет ответ. Между этими точками работает поиск, поэтому неоднозначность определяется по базе, а не по форме вопроса.

**Главное правило узла.** Неоднозначность определяется **по каталогу контрагентов и договоров**: сколько карточек каталога совпало с упоминанием в вопросе (с учётом истории). Не по наличию кавычек, правовой формы, длины вопроса или слова «договор».

## 2. As-is на `d1f068c`
`_is_ambiguous_contract` (pipeline.py 285-296) возвращает «нужно уточнение», если одновременно: в вопросе есть «договор»; `_has_counterparty_or_contract_id` (269-282) ложно; нет «типовых якорей» («регламент», «правоспособ», «аренд», «поставк», «кредитн»); уникальных токенов длиннее 2 символов меньше 8. Якорем считается **любое** из: правовая форма (`_LEGAL_FORM_RE`, 261), любое имя в кавычках (`_QUOTED_NAME_RE`, 262), номер (`_CONTRACT_NO_RE`, 263-266, только кириллица «а-», «п-», «пт-»), слова «инн», «контрагент», «номер договора», фрагменты демо-сущностей (`_DEMO_ENTITY_FRAGMENTS`, 251-260: «северн», «альфа-трейд», «альфа-трейдинг», «а-08», «п-17», «пт-05»). Вызов в `answer_question` (370) дополнительно пропускает вопросы со словом «ндс».

Наблюдаемое поведение (артефакт [`../07-tests/artifacts/asis-d1f068c-lexical-run.md`](../07-tests/artifacts/asis-d1f068c-lexical-run.md)):

## 3. To-be спецификация
### 3.1. Каталог (строит ND1, читает ND4)
Для каждой стороны договора, кроме ООО «Меридиан»: `card_id`, `name_canonical` («ООО «Альфа-Трейдинг»»), `name_core` («альфа-трейдинг»), `core_tokens` (`["альфа", "трейдинг"]`) и их основы по Snowball [S-27], `inn`, `doc_ids` (договоры и связанные ДС), `subject` (предмет договора одной строкой из п. 1.1: «офисная мебель и оборудование», «компьютерная техника»). На текущей базе три карточки: «Северный Склад» (А-08/2024), «Альфа-Трейд» (П-17/2024 + ДС № 1), «Альфа-Трейдинг» (ПТ-05/2023) ([`../02-architecture/03-data-model-and-kb.md`](../02-architecture/03-data-model-and-kb.md) §1.1).

### 3.2. Извлечение упоминаний
Источники упоминаний в порядке силы: номер договора (после нормализации латиницы), ИНН, полное имя с правовой формой, имя в кавычках, голое имя после предлогов «с», «у», «от», «по договору с», предмет договора («компьютеры», «мебель»), реплики пользователя в истории, вопрос ассистента в истории, на который пользователь ответил.

### 3.3. Сопоставление с каталогом
1. Номер или ИНН: точное совпадение ключа → ровно одна карточка.
2. Имя: каждый токен упоминания приводится к основе Snowball [S-27] и должен **точно совпасть** с одной из основ `core_tokens` карточки; карточка совпала, если совпали все токены упоминания. Проверено на реализации Snowball (пакет `snowballstemmer`, 10.11.2026): «Альфой», «Альфа», «Альфе» дают основу «альф»; «Трейдинга» даёт «трейдинг»; «трейд» остаётся «трейд». Поэтому «Альфой» → {альф} совпадает с обеими «Альфа-…», а «Альфа-Трейд» → {альф, трейд} совпадает только со своей карточкой. Префиксное сравнение основ отвергнуто: «трейд» является префиксом «трейдинг», и полное имя «Альфа-Трейд» ложно совпало бы с двумя карточками (`UT-CAT-03`).
3. Предмет: «компьютеры» сужает «Альфа» до ПТ-05/2023 только если `subject` карточки содержит основу; это сигнал слабее имени и используется лишь для сужения уже найденного множества.
4. История: если в предыдущих репликах пользователь назвал одну карточку, а ассистент спрашивал «… или …?», ответ пользователя закрывает выбор. Реплики ассистента дают только кандидатов (I7).

### 3.4. Решение
| Совпало карточек | Ответы по кандидатам | Исход |
|---|---|---|
| 0 | | сущности нет; вопрос идёт без фильтра по договору (общие нормы, регламент) |
| 1 | | фильтр по `doc_ids` карточки + общие документы (регламенты, письма, законы) |
| 2-3 | одинаковые (после ND6 проверки) | ответ, где обе ссылки названы; статус по ND6 |
| 2-3 | различаются | `clarify` с вариантами: для каждой карточки краткий ответ с проверенной цитатой; без выбора за пользователя |
| > 3 или ответы в разных разделах базы | | `clarify` с перечнем карточек без ответов по каждой |

`clarify.options[]`: `{card_id, label: "ООО «Альфа-Трейдинг», № ПТ-05/2023", claim, citation}`. Каждый `claim` проходит ту же проверку, что обычный ответ (ND6). Кнопка варианта в UI отправляет уточнённый вопрос с историей (ND8).

### 3.5. Что делает S7 (LLM) и чего не делает
S7 возвращает JSON (схема в 05-rag/02 §3 S7): `intent`, `standalone_question`, `entities`, `event_date`, `search_queries`, `premises`. Сущности, которых нет в каталоге, отбрасываются. **Решение о неоднозначности S7 не принимает**: флаг `needs_clarification` модели используется только как дополнительный сигнал для журнала и eval.

## 4. Почему так
1. **Уточнение по базе, а не по форме вопроса.** Неоднозначность «какая Альфа» является свойством базы: в ней два контрагента с общим корнем. Длина вопроса и кавычки не несут этой информации. Это прямо видно в демо-наборе организаторов: в Q17 ассистент в истории сам задаёт уточнение с двумя вариантами («Альфа-Трейд» или «Альфа-Трейдинг»?), а эталон отвечает по выбранному договору [K-DEMO]. Значит, организаторы считают правильным уточнение **с именами кандидатов**.
2. **Одно хорошее уточнение даёт больше, чем угадывание.** Aliannejadi et al. на Qulac показывают, что одно удачное уточняющее вопрос-ответ на оракульной модели поднимает P@1 более чем на 170% [S-84]; в разговорной системе, которая возвращает один ответ, это особенно важно.
3. **LLM плохо определяет неоднозначность сама.** CLAMBER: современные LLM ограниченно полезны в распознавании и прояснении неоднозначных запросов, CoT и few-shot дают лишь маргинальный прирост и могут добавлять самоуверенность [S-85]. Поэтому решение детерминированное, по каталогу, а модель только формулирует.
4. **Промах документа является главным риском юридического RAG.** В базах со структурно похожими документами поиск часто берёт фрагмент из неверного документа (DRM) [S-83]; два договора поставки с «Альфа-…» являются ровно таким случаем. Выбор договора «наугад» даёт уверенный ответ с цитатой из чужого договора, то есть misgrounding [S-49].
5. **Уточнять при сомнении в цели, это принцип, а не наша выдумка.** Руководство Microsoft по взаимодействию человека и ИИ (18 принципов, проверены с 49 практиками на 20 продуктах): G10 «Scope services when in doubt», то есть при неуверенности в цели пользователя уточнять или сужать ответ, а не угадывать; G11 требует объяснять, почему система так сделала [S-138]. У нас G10 это `clarify` с кандидатами из каталога, G11 это `missing` и кнопки вариантов с именами договоров.
6. **Правовая форма и кавычки не различают контрагентов, различают ИНН и номер договора.** Фирменное наименование по закону состоит из правовой формы и собственно имени [S-148], поэтому «ООО» есть у обоих кандидатов: в базе это ООО «Альфа-Трейд» и ООО «Альфа-Трейдинг». As-is эвристика `d1f068c` считает правовую форму и имя в кавычках достаточным якорем (D18), хотя по смыслу это ничего не сужает. Уникальность имён регистрирующий орган не проверяет, и при совпадении определяющими являются ОГРН и ИНН [S-149]. Поэтому в §3.3 ключи «номер договора» и «ИНН» стоят первыми и дают ровно одну карточку, а имя даёт только множество кандидатов.
7. **Уточнение с вариантами, а не голое.** Голое «уточните договор» на одиночном вопросе почти наверняка проигрывает бейзлайну у судьи, который сравнивает полезность [K-REG §8]; вариант с цитатой даёт судье проверяемое содержание. Это гипотеза; проверка двумя сабмитами описана в 05-rag/02 §5.

## 5. Отвергнутые альтернативы
| Альтернатива | Почему нет |
|---|---|
| Эвристика по кавычкам, правовой форме и длине (as-is) | ошибается в обе стороны (таблица §2); не переносится на закрытую базу с другими именами |
| Список демо-фрагментов имён в коде | подгонка под публичный набор (как D9); на private имена другие |
| Решение о `clarify` моделью | недетерминированно [S-77], слабая надёжность [S-85] |
| Всегда выбирать «самый похожий» договор | уверенный ответ по чужому договору; судья обнуляет выдуманное [K-REG §8] |
| Всегда отвечать по всем кандидатам без `clarify` | при двух кандидатах это допустимо только если ответы совпадают; иначе ответ смешивает договоры |

## 6. На что влияет
`clarify` (с вариантами и без), фильтр по договору для всех последующих узлов, `missing` при `limited` (например, «гарантийный талон» по ПТ-05/2023 п. 6.1). Критерии: достоверность 25%, интерфейс 15% (кнопки вариантов), скорость (ответы по кандидатам стоят дополнительных генераций: максимум 3).
