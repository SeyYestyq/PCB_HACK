Дополняет `01`-`05`, не заменяет их: каждая величина с числом и причиной. Токены из `02-design-system.md`; если значение уточняет `02`/`03`/`04`, оно помечено словом **Уточнение**, сводка в §8.2.

## 0. Как читать значения

- Все размеры в CSS px; 1 CSS px = 1 pt HIG на стандартной плотности (как в `02`).
- Запись: **токен → px → почему**. Основание одного из типов: гештальт (близость, общая область), закон Фиттса, HIG, WCAG 2.2, юридическое чтение (сверка формулировок, длина строки), технический (раскладка не прыгает, CLS).
- Волосяная линия 1px вне шкалы 4/8: «16 + линия + 16» считается как 32.
- Коды источников:
  - **[HIG-L]** Apple HIG [Layout](https://developer.apple.com/design/human-interface-guidelines/layout); **[HIG-A]** [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility); **[HIG-M]** [Motion](https://developer.apple.com/design/human-interface-guidelines/motion); **[HIG-LD]** [Loading](https://developer.apple.com/design/human-interface-guidelines/loading); **[HIG-T]** [Typography](https://developer.apple.com/design/human-interface-guidelines/typography); **[HIG-B]** [Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons).

  - **[WK]** WebKit, T. Horton, [Designing Websites for iPhone X](https://webkit.org/blog/7929/designing-websites-for-iphone-x/): `viewport-fit=cover`, `env(safe-area-inset-*)`, `max()`.

## 1. Безопасные зоны и края экрана

### 1.1. Что говорит первоисточник

- HIG Layout [HIG-L]: «A safe area defines the area within a window that isn't covered on the edge by a hardware feature or another view within the window, like a toolbar, tab bar, or status bar. Respecting the safe area is essential to make sure system UI and hardware features like the Dynamic Island don't obstruct content and controls».
- Там же: «You can help ensure an adaptable interface by respecting system-defined safe areas, margins, and guides».
- Там же про фон: «For full-screen background content, be sure to extend it underneath sidebars, toolbars, and tab bars to fit the entire screen or window». Отсюда наше правило: фон до края, содержимое внутри.
- Там же, раздел macOS: «Avoid placing controls or critical information at the bottom of a window. People often move windows so that the bottom edge is below the bottom of the screen». Это касается нашего десктопного композера (§1.6).
- WebKit [WK]: страница с `viewport-fit=cover` раскладывается на весь экран, и тогда «it is immediately clear why it is important to respect the system's safe area insets: some of the page's content is obscured by the device's sensor housing, and the bottom navigation bar is very hard to use». Отступы берутся из `env(safe-area-inset-top|right|bottom|left)`.
- WebKit [WK], главное для нас: **«Safe area insets are not a replacement for margins»**. В портретной ориентации левая вставка равна 0px, и текст лёг бы вплотную к краю, поэтому нужен `max(базовый отступ, env(...))`.
- UIKit [UIK]: `safeAreaInsets` и `safeAreaLayoutGuide` сообщает система для конкретного устройства, ориентации и окружения; приложение их читает, а не задаёт. На iPhone с Face ID в портретной ориентации нижняя вставка обычно 34 pt: это **направляющая для макета**, не значение для кода. Верхняя вставка у моделей разная (зависит от выреза или Dynamic Island), поэтому в этой главе список чисел верха не ведём: верх всегда берётся у системы.

### 1.2. Перевод на веб: что есть у браузера вместо `safeAreaInsets`

| Нативный iOS | Наш веб | Примечание |
|---|---|---|
| `view.safeAreaInsets` | `env(safe-area-inset-top/right/bottom/left)` | Работает, только если в `<meta name="viewport">` указан `viewport-fit=cover`. Без него Safari сам ужимает страницу внутрь безопасной зоны и красит поля цветом фона [WK] |
| `safeAreaLayoutGuide` | Контейнер с `padding: max(базовый, env() + зазор)` | См. токены §1.3 |
| Направляющая 34 pt в макете | Направляющая 34 px в макете мобильного кадра 390x844 и 430x932 | Только для макета. В коде 34 не пишется |
| Высота экрана без системных панелей | `100dvh` (с запасным `100vh`) | `100vh` в мобильном Safari равен высоте с убранной панелью адреса, поэтому низ страницы, включая композер, может оказаться под панелью |

**Решение.** На мобильном вебе ставим `viewport-fit=cover`. Почему не оставить автоматические поля Safari: тогда шапка (белая) и нижний лист источников (белый) обрываются цветными полями фона холста `#F8F8FC` у выреза и у полоски, а при повороте устройства поля меняются. С `cover` фон шапки, листа и скрима уходит до физического края (HIG «extend it underneath»), а каждый текст и контрол получает отступ из `env()`. Цена решения: **каждый** прилипающий к краю элемент обязан взять вставку. Перечень таких элементов закрыт в §1.4; новый элемент у края без строки в этой таблице не проходит ревью.

Мета-тег (единственный допустимый):

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
<meta name="theme-color" content="#FFFFFF" media="(prefers-color-scheme: light)">
<meta name="theme-color" content="#12132B" media="(prefers-color-scheme: dark)">
```

Запрещено дописывать `maximum-scale=1` и `user-scalable=no`: это отключает масштабирование страницы, нарушает HIG-A «Support larger text sizes» и WCAG [1.4.4 Resize Text](https://www.w3.org/TR/WCAG22/#resize-text). `theme-color` совпадает с цветом шапки (`surface`), чтобы полоса браузера и шапка читались одной поверхностью.

### 1.3. Токены

```css
:root {
  /* Системные вставки. 0px там, где система их не сообщает (десктоп, Android без выреза) */
  --safe-top:    env(safe-area-inset-top, 0px);
  --safe-right:  env(safe-area-inset-right, 0px);
  --safe-bottom: env(safe-area-inset-bottom, 0px);
  --safe-left:   env(safe-area-inset-left, 0px);

  /* Проектный зазор над системной зоной: кнопка не касается направляющей */
  --edge-gap: var(--space-2);                 /* 8px */

  /* Итоговые отступы края = max(базовый отступ, вставка + зазор) [WK] */
  --edge-x:      max(var(--space-4), calc(var(--safe-left)  + var(--edge-gap)));  /* слева */
  --edge-x-r:    max(var(--space-4), calc(var(--safe-right) + var(--edge-gap)));  /* справа */
  --edge-bottom: max(var(--space-4), calc(var(--safe-bottom) + var(--edge-gap))); /* низ */
  --edge-top:    var(--safe-top);   /* шапка сама даёт 16 сверху внутри своих 56, зазор не добавляется */

  --app-height: 100dvh;
}
@supports not (height: 100dvh) { :root { --app-height: 100vh; } }
```

Почему `max(16, вставка + 8)`, а не `вставка + 16` и не просто `34`:
1. **Не `34`.** UIKit [UIK] и WebKit [WK]: значение берут у системы. На iPhone с кнопкой «Домой» нижняя вставка 0, на Face ID в Safari она меняется в зависимости от того, развёрнута ли нижняя панель браузера, на Android с жестовой навигацией своя. Захардкоженные 34 дают лишние 34 px пустоты на половине устройств и недостаток на будущих.
2. **Не `вставка + 16`.** На Face ID в standalone-режиме это 34 + 16 = 50 px до низа контейнера композера, плюс его внутренний padding 12, итого кнопка «Спросить» в 62 px от края. Это тратит высоту экрана, а она на мобильном главный ресурс ленты.
3. **`max(16, вставка + 8)`.** Без системной зоны остаётся обычный край 16 (`space-4`, тот же, что поля ленты на мобильном, §2.2). С зоной кнопка встаёт над направляющей с зазором 8 плюс внутренний padding композера 12: нижний край кнопки «Спросить» оказывается в 34 + 8 + 12 = **54 px** от физического края, вне полосы, где Safari перехватывает свайп «домой». 8 выбрано как минимальный шаг ритма (`space-2`), который на экране читается как намеренный зазор, а не как касание.

Поведение Safari, которое надо проверить на устройстве (а не принимать на веру): при развёрнутой нижней панели адреса вставка снизу может приходить 0, потому что полоску закрывает сама панель браузера, а в режиме «На экран Домой» (standalone) приходит полная вставка. Формула выше корректна в обоих случаях: отступ берёт код, а не макет.

### 1.4. Элемент за элементом: что уходит под край, что нет

Правило: **фон, скрим и тени могут доходить до физического края; текст, иконки, контролы и фокус-кольца не могут.**

| Элемент | Фон до края | Содержимое | CSS (мобильный < 768) | Почему |
|---|---|---|---|---|
| Шапка 56 | Да: фон `surface` и нижняя линия заходят под вырез / Dynamic Island | Логотип, название, кнопки: внутри | `padding-top: var(--edge-top); height: calc(56px + var(--safe-top)); padding-inline: var(--edge-x) var(--edge-x-r)` | Верх у моделей разный, поэтому высота шапки = 56 + вставка, а не фиксированные 100 или 103 |
| Лента | Да (фон `canvas`) | Текст и чипы: `padding-inline: var(--edge-x) var(--edge-x-r)` | | В альбомной ориентации вырез оказывается слева или справа [WK]; текст ответа не должен уйти под него |
| Зона композера (прилипает к низу) | Да: полоса `canvas` под композером доходит до нижнего края, лента прокручивается под ней | Контейнер композера и кнопка «Спросить»: над `--edge-bottom` | `padding-bottom: var(--edge-bottom)` | Кнопка над направляющей с зазором; HIG-L «Respecting the safe area is essential» |
| Дисклеймер под композером | Да | Текст внутри | Входит в зону композера, нижний отступ тот же | Текст держим внутри безопасной зоны |
| Нижний лист «Источники» (85% высоты) | Да: белый фон листа уходит до низа, под полоску | Список карточек, кнопка «Закрыть»: внутри | `padding-bottom: var(--edge-bottom)` у прокручиваемого тела; последняя карточка заканчивается над зоной | Последняя кнопка «Открыть в документе» в списке не должна оказаться на полоске при прокрутке до конца |
| Полноэкранный документ | Да | Шапка документа: `padding-top: var(--safe-top)`; тело: `padding-bottom: var(--edge-bottom)` | | Конец документа читается полностью, не под полоской |
| Drawer истории (слева) | Да, на всю высоту | Пункты: `padding-top: var(--safe-top)`, `padding-left: var(--edge-x)`, последний пункт над `--edge-bottom` | | В альбомной ориентации вырез слева |
| Скрим `--color-scrim` | Да, весь экран, включая зоны | Содержимого нет | `inset: 0` на `position: fixed` | Затемнение под вырезом выглядит цельным |
| Тост | Нет фона до края (плавающий) | Весь тост над зоной композера на 16 | `bottom: calc(var(--composer-zone-h) + 16px)` | Тост не закрывает композер и не встаёт на полоску |
| Фокус-кольцо | Нет | Кольцо 2px + зазор 2px целиком внутри безопасной зоны | Отступы элементов у края ≥ 4px больше кольца: обеспечено `--edge-x ≥ 16` | Кольцо, обрезанное краем экрана или вырезом, не видно: WCAG [2.4.11 Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) |
| Поповер ссылки, тултип | Нет | Позиционирование с ограничением по безопасной зоне | `collision padding` = `--edge-x` по бокам, `--safe-top + 8` сверху | Иначе поповер у верхнего чипа уйдёт под Dynamic Island |

### 1.5. Схема «до / после» для нашего композера (мобильный, Face ID, standalone)

```
ДО (ошибка)                                  ПОСЛЕ (наша спецификация)
┌──────────────────────────────┐             ┌──────────────────────────────┐
│ ...лента...                  │             │ ...лента...                  │
│┌────────────────────────────┐│             │┌────────────────────────────┐│
││ Вопрос по базе...          ││             ││ Вопрос по базе...  [Спросить]│← кнопка 44
││                 [Спросить] ││             │└────────────────────────────┘│   над зазором
│└────────────────────────────┘│ ← bottom:0  │  ↕ 12 padding контейнера      │
│▔▔▔▔▔▔▔▔▔▔▔ ▬▬▬▬▬ ▔▔▔▔▔▔▔▔▔▔▔▔│ полоска     │  ↕ 8  --edge-gap              │
└──────────────────────────────┘ на кнопке   │- - - - - направляющая 34 - - -│
                                             │          ▬▬▬▬▬                │ фон canvas до края
                                             └──────────────────────────────┘
  кнопка в зоне свайпа: тап читается          нижний край кнопки в 54 px от края;
  как жест «домой», приложение сворачивается  в Safari с панелью: max(16, 0+8) = 16
```

Почему это критично именно здесь: юрист нажимает «Спросить» после набора длинного вопроса с номерами пунктов. Тап у края уводит в систему, и пользователь не понимает, что виновата кнопка у самого края; набранный вопрос может потеряться, а это нарушает правило `03 §13` «вопрос не теряется».

### 1.6. Десктоп: края окна, а не выреза

На десктопе вставки равны 0, но у края окна есть свои риски.

| Край | Риск | Спецификация | Основание |
|---|---|---|---|
| Верх | Шапка браузера и вкладки уже вне страницы; при установке как PWA с `display: standalone` заголовок окна рисует ОС | Шапка 56 начинается с `top: 0`; `display_override: window-controls-overlay` **не** включаем, иначе пришлось бы раскладывать шапку по `env(titlebar-area-*)` ради нулевой пользы | Простота; HIG-L «respecting system-defined safe areas» |
| Низ | HIG macOS: «Avoid placing controls or critical information at the bottom of a window». Композер чата стоит внизу | Принятое отступление от HIG с тремя мерами: (1) клавиша `/` ставит фокус в композер из любой точки (`02 §9`); (2) минимальная высота окна, при которой композер прилипает, 560 px, ниже он становится обычным блоком в конце ленты и прокручивается к нему; (3) нижний отступ зоны композера 16, а не 0, чтобы кнопка не касалась края окна | Конвенция чатов сильнее: юрист ищет поле ввода внизу; клавиатурный путь не зависит от края |
| Право | Панель «Источники» прилегает к краю окна, ручка ресайза слева от неё, у края нет контролов меньше 32 | Кнопка «Свернуть панель» в 16 от правого края | Цели у самого края окна в браузере не дают выигрыша Фиттса (за краем окна ещё экран), поэтому отступ обычный |
| Лево | История 264 | Пункты с padding 12 внутри колонки | |

### 1.7. Клавиатура на мобильном

Когда открыта экранная клавиатура, полоски домашнего индикатора под композером нет: её закрывает клавиатура. Значит, зазор над вставкой в этот момент лишний.

| Состояние | Нижний отступ зоны композера | Как определить |
|---|---|---|
| Клавиатура закрыта | `var(--edge-bottom)` | По умолчанию |
| Клавиатура открыта | `var(--space-2)` (8) | `window.visualViewport` `resize`: если `visualViewport.height < innerHeight - 120`, на `<html>` ставится `data-kb="open"`. Порог 120 отсекает изменение высоты при сворачивании панели Safari |
| Chrome Android | Тот же результат через `<meta name="viewport" ... interactive-widget=resizes-content>` | Атрибут поддерживается Chrome; Safari его игнорирует, поэтому остаётся вариант через `visualViewport` |

Проверка обязательна на реальном iPhone и Android: поведение панелей браузера различается по версиям.

### 1.8. Как правильно / как нельзя

| Как правильно | Как нельзя |
|---|---|
| Фон шапки, листа, скрима до физического края | Белые «поля» вокруг шапки от автоматических вставок Safari |
| «Спросить» и «Закрыть» листа над `--edge-bottom` с зазором 8 | Кнопка с `bottom: 0` или ровно на линии 34 |
| `max(16px, calc(env(safe-area-inset-bottom) + 8px))` | `padding-bottom: 34px` |
| Высота шапки `calc(56px + env(safe-area-inset-top))` | Фиксированная высота шапки «под конкретный айфон» |
| `100dvh` для каркаса | `100vh`, из-за которого композер уходит под панель Safari |
| Поля ленты `max(16px, inset + 8px)` слева и справа | Текст ответа под вырезом в альбомной ориентации |
| Масштаб страницы разрешён | `user-scalable=no`, `maximum-scale=1` |

### 1.9. Проверка перед передачей макета

1. В мобильных кадрах 390x844 и 430x932 стоят направляющие: снизу 34, сверху вставка из шаблона конкретной модели. Нужны минимум два кадра с разным верхом. Направляющие только в макете.
2. Ни один текст, иконка, контрол и фокус-кольцо не пересекает направляющие; фон пересекает.
3. Между направляющей 34 и ближайшей кнопкой видно 8 + внутренний padding.
4. В коде нет числовых отступов под системные зоны: `rg "34px" apps/web/src` пусто, у каждого прилипающего элемента отступ через `env()` или токены §1.3.
5. Проверены: iPhone с Face ID в Safari (панель развёрнута и свёрнута), тот же iPhone в standalone, альбомная ориентация, Android с жестовой навигацией, десктоп при высоте окна 560 и 1080.

## 2. Отступы до последнего пикселя

### 2.1. Правила, которые проверяются у каждого числа

| # | Правило | Значение | Основание |
|---|---|---|---|
| П1 | Только шаги шкалы `02 §4`: 4, 8, 12, 16, 20, 24, 32, 40, 48, 64 | Любое другое число в CSS отклоняется на ревью | unslop «Arbitrary values → steps on the 4px scale» (`02 §4`) |
| П2 | Близость: зазор внутри группы меньше зазора между группами минимум в 1.5 раза | Например, 8 внутри, 12 и больше снаружи; 32 внутри обмена, 48 между обменами | Гештальт, HIG-L «Group related items» |
| П3 | Общая область: если группа обведена рамкой или фоном, зазор между такими группами может быть меньше их внутреннего padding | Карточки источников: padding 16, зазор 8 | Гештальт «common region»: рамка уже группирует, лишний воздух только удлиняет панель |
| П4 | Между соседними интерактивными целями не меньше 8 | Кнопки в ряду 8, чипы в тексте 4 (исключение «Inline» WCAG 2.5.8, дублируются целями 56) | HIG-A «Consider spacing between controls as important as size»; `02 §4` |
| П5 | Высота строки текста кратна 4, кроме 26 (`type-body`) и 18 (`type-meta`) | Вокруг 26 и 18 отступы всё равно кратны 4 | `02 §6.3` |
| П6 | Вертикальный padding контрола = (высота контрола - line-height подписи) / 2 | 44: (44 - 20) / 2 = 12; 32: (32 - 20) / 2 = 6; бейдж 24: (24 - 20) / 2 = 2 | Подпись по центру без «магических» сдвигов; 6 и 2 являются производными, не токенами, и записываются через `calc` |
| П7 | Волосяная линия 1px не входит в шкалу | «16 + линия + 16» считается как 32 | §0 |

|---|---|---|
| Padding контейнера | 8 | Экономия высоты экрана |

### 3.4. Как юрист отличает слова ассистента от слов документа

Одного признака мало (WCAG 1.4.1 и HIG Color: не полагаться только на один канал). Цитата отличается пятью независимыми признаками:

| # | Признак | Текст ассистента | Слова документа |
|---|---|---|---|
| 1 | Гарнитура | Golos Text, гротеск | PT Serif, засечки |
| 2 | Кегль при равной x-height | 16 / 14 | 17 / 15 |
| 3 | Линия слева | нет | 2 px `accent` |
| 4 | Кавычки | нет | «ёлочки» вокруг цитаты в карточке и поповере |
| 5 | Адрес рядом | номер чипа [1] | документ, пункт, редакция над цитатой |
| 6 | Разметка | `<p>` | `<blockquote cite="#doc-id">` + `<cite>` с адресом; скринридер объявляет «цитата» |

Курсив у ассистента запрещён, потому что курсив встречается внутри документов и сохраняется в цитатах (`01 §6.3`). Если бы ассистент выделял курсивом, признак 1 частично размывался бы.

Правило для всех исходов: **ровно один `type-headline` в ответе.** У `grounded` это вывод, у остальных заголовок баннера. Исключение: `premise_corrected`, где после баннера идёт вывод; там вывод набирается `type-body-strong`, чтобы на экране не было двух равных заголовков (HIG-L «Order content by relative importance»).

## 4. Движение

### 4.1. Принципы

1. **Движение объясняет, откуда пришёл объект и куда ушёл, и больше ничего.** HIG-M: «Add motion purposefully, supporting the experience without overshadowing it. Don't add motion for the sake of adding motion. Gratuitous or excessive animation can distract people and may make them feel disconnected or physically uncomfortable».
2. **Коротко.** NN/g [NNG-AN]: «the duration of most animations should be in the range of 100-500 ms»; «In most cases, a range of 100-400 ms is appropriate, with 400ms being a very slow animation, to be used only for big movements across large screens»; «It is far more common for animations to be too long than too short». Наш максимум 300 (прокрутка документа), панели 240.
3. **Замедление в конце.** NN/g [NNG-AN]: «Most frequently, you'll want to use an ease-out animation, that starts quickly but slows down»; ease-in на выходе «can feel unresponsive». Поэтому одна кривая `cubic-bezier(.2,0,0,1)` (быстрый старт, долгое торможение) на вход и на выход; выход короче входа.
4. **Не ждать анимацию.** HIG-M: «Let people cancel motion. As much as possible, don't make people wait for an animation to complete before they can do anything». Любая анимация прерывается следующим действием; кнопки активны с первого кадра.
5. **Движение не единственный носитель смысла.** HIG-M «Make motion optional... avoid using it as the only way to communicate important information». Каждая анимация дублируется состоянием (цвет, текст, `aria-*`), которое остаётся после неё.
6. **Уменьшение движения.** HIG-A: при Reduce Motion уменьшать «automatic and repetitive animations, including zooming, scaling, and peripheral motion», заменять перемещения на затухания. `02 §8.2` фиксирует для нас строже: при `prefers-reduced-motion: reduce` все переходы 0 ms. Это решение не меняем; в §8 записано предложение разрешить там затухания 120 ms, как допускает HIG.

### 4.2. Токены (из `02 §8.2`, без изменений)

```css
:root {
  --ease-standard: cubic-bezier(.2, 0, 0, 1);
  --motion-fast:  120ms;  /* hover, pressed, затухание мелких элементов */
  --motion-base:  200ms;  /* раскрытие карточки, появление бейджа и ответа */
  --motion-panel: 240ms;  /* выезд панели, листа, drawer; выход 200 */
  --motion-scroll: 300ms; /* целевая длительность прокрутки к фрагменту */
}
@media (prefers-reduced-motion: reduce) {
  :root { --motion-fast: 0ms; --motion-base: 0ms; --motion-panel: 0ms; --motion-scroll: 0ms; }
  html { scroll-behavior: auto; }
}
```

Анимируются только `opacity`, `transform`, `background-color`, `border-color`, `color`. Никогда `height`/`width`/`top` (кроме раскрытия карточки через `grid-template-rows`, §4.3), никогда `filter: blur` (HIG-A «Avoiding animating into and out of blurs»; `05` R7).

### 4.4. Что запрещено и почему

| Запрет | Почему | Источник |
|---|---|---|
| Посимвольная «печать» ответа и мигающий курсор | Ответ показывается только после проверки ссылок; печать показала бы непроверенный текст и мигала бы во время чтения | `05` R9; HIG-A «Be cautious with fast-moving and blinking animations»; WCAG 2.2.2 |

## 5. Скелетоны и загрузка, кадр за кадром

### 5.1. Решения и их основания

| Решение | Основание |
|---|---|
| Скелетон только там, где известна форма будущего содержимого: карточки источников, тело документа, список истории | NN/g [NNG-SK]: скелетон «mimics the layout of the page»; скелетон из одной рамки без содержимого «essentially equivalent to a spinner» и не рекомендуется |
| **В ленте нет текстового скелетона ответа**, только строка стадии | Исход неизвестен до конца проверки: это может быть баннер `abstain`, а не текст. Скелетон из трёх строк текста пообещал бы ответ, которого может не быть. Это решение следует из fail-closed, а не из эстетики |
| Скелетоны статичные: без shimmer и без пульсации | `03 §9.2` «без shimmer», `02 §8.2`. NN/g отмечает, что анимация скелетона может отвлекать и создавать проблемы доступности [NNG-SK]. Движется на экране одно: спиннер стадии (M10), и только первые 5 с. Три пульсирующих зоны (лента, панель, документ) спорили бы за внимание |
| Меньше 1 с: ничего не показываем, кроме строки стадии | NN/g: «If a page takes less than 1 second to load, skeleton screens or spinners aren't necessary... the quick flashing page can cause users to feel like they can't keep up». Поэтому скелетон документа появляется только если загрузка дольше 300 мс, а появившись, держится минимум 300 мс (без вспышки) |
| 2-10 с: скелетон + стадии | NN/g: скелетоны и спиннеры «best used when the page takes 2-10 seconds» |
| Больше 10 с: явное сообщение | NN/g: «Anything above 10 seconds requires an explicit estimation of duration»; оценки длительности у нас нет, поэтому честный текст `progress.slow` и возможность остановить [NNG-RT] |
| Показать что-то сразу | HIG-LD: «If you make people wait for loading to complete before displaying anything, they can interpret the lack of content as a problem». Строка стадии появляется в первом кадре после отправки |
| Не блокировать работу | HIG-LD: «Let people do other things in your app or game while they wait». Во время ответа можно читать прошлые ответы, открывать документы, прокручивать ленту |

## 10. Скругления

Четыре токена из `02 §7.1`, других радиусов нет.

| Токен | px | Поверхности |
|---|---|---|
| `radius-xs` | 2 | Подсветка `<mark>` в документе, полосы скелетона, ручка нижнего листа 32x4, фокус-кольцо inline-ссылки |
| `radius-sm` | 4 | Кнопки L и M, поле ввода, бейдж статуса, чип «[1]», строка «Оснований», пункт истории (предложение: в `03 §14.2` радиус не задан), тост, тултип, блок-заглушка кнопок в скелетоне |
| `radius-md` | 8 | Композер, блок реплики пользователя, баннер исхода, карточка источника, меню «⋯», поповер ссылки (предложение: тот же уровень 2, что меню) |
| `radius-lg` | 12 | Диалог подтверждения, нижний лист (только верхние углы) |
| 0 | 0 | Шапка, колонка истории, панель «Источники», лист документа поверх ленты: они прилегают к краю окна или соседней колонке |

Правила:
1. Вложенный элемент скруглён не больше родителя: кнопка 4 внутри карточки 8, карточка 8 внутри листа 12.
2. Фокус-кольцо повторяет радиус элемента (`outline` следует `border-radius`), отдельного радиуса у кольца нет.
3. Круг допустим только как геометрия значка: спиннер 16, точка редакции 6, маркер списка 4. Это не радиус контрола.

| Как правильно | Как нельзя |
|---|---|
| Кнопка 4, карточка 8, диалог 12 | Радиус 16 и больше у любой поверхности |
| Чип «[1]» 4, квадратный по форме номера | Pill `999px` у кнопок, бейджей, чипов |
| Блок реплики 8, как у карточек | Скругление одного угла «хвостиком» в стиле мессенджера |
| Нижний лист: 12 только сверху | Скруглённые нижние углы у листа, прижатого к краю |

## 12. Генерация ответа: что видно, пока ассистент работает

### 12.1. Почему нет «печатающихся точек»

Индикатора из трёх прыгающих точек, посимвольной печати, shimmer и процента в продукте нет (`03 §11.1`, `05`). Причины:

1. **Fail-closed.** Ответ показывается только после проверки ссылок. Точки «собеседник печатает» и посимвольный вывод обещают текст, который пишется прямо сейчас; у нас текст может так и не появиться (исход `abstain` или `refuse_role`).
2. **Точки ничего не сообщают.** Строка стадии говорит, что именно происходит: ищу, сверяю, проверяю ссылки. Это и есть видимый контроль достоверности.
3. **Движение во время чтения.** Бесконечная анимация мешает читать прошлые ответы и нарушает WCAG 2.2.2 после 5 с.

**Чем заменено:** строка стадии 24 px (спиннер 16 + 8 + текст `progress.*`) слева в ленте на месте будущего бейджа; спиннер вращается не дольше 5 с, затем статичная иконка `loader`; справа в панели три статичных скелетона карточек по 202 px.

### 12.2. Раскадровка

| Кадр | Время | Слева: лента | Справа: панель «Источники» | Композер |
|---|---|---|---|---|
| L0 | 0 | Реплика пользователя; «Ассистент» без времени; спиннер + «Ищу положения в базе» (`progress.search`) | «К ответу от 22:41» + 3 скелетона по 202, зазор 8 | Поле очищено, `readonly`; «Остановить» |
| L1 | событие или 1,5 с | «Сверяю ответ с найденными фрагментами» (`progress.verify`) | без изменений | |
| L2 | событие или 4 с | «Проверяю ссылки» (`progress.cite`) | без изменений | |
| L3 | 5 с | Спиннер останавливается: статичная иконка + текст стадии | без изменений | |
| L4 | 10 с | Под стадией «Ответ готовится дольше обычного. Можно остановить и уточнить вопрос» (`progress.slow`) | без изменений | |
| L5 | ответ проверен | Бейдж встаёт на место строки стадии (обе 24), ответ появляется целиком, `opacity` 200 | Скелетоны → карточки, 200; лишние уходят затуханием; ноль карточек → «Для этого ответа подтверждающих положений не найдено» | «Спросить» |
| L6 | 60 с | Баннер системной ошибки `timeout`, вопрос возвращается в поле | Источники предыдущего ответа | |
| Стоп | по кнопке | «Ответ остановлен. Вопрос можно изменить и отправить снова» (`progress.stopped`) | Скелетоны удалены | Вопрос в поле, фокус в поле |

Смена стадии: затухание 120 + 120, каждая стадия видна не меньше 600 мс. Таймеры 1,5 с и 4 с работают только без событий SSE и не обгоняют их. При `prefers-reduced-motion: reduce` все переходы 0 ms, спиннер сразу статичный (`02 §8.2`). Доступность: стадия в `role="status" aria-live="polite"`, на ответе `aria-busy="true"` до L5. Во время генерации можно читать прошлые ответы и открывать документы; лента не прокручивается сама, если пользователь ушёл выше (M13).

### 12.3. Как правильно / как нельзя

| Как правильно | Как нельзя |
|---|---|
| Строка стадии с текстом из `progress.*` | Три прыгающие точки, «Ассистент печатает…», «Думаю…» |
| Ответ целиком после проверки | Посимвольная печать, мигающий курсор |
| Спиннер 16 не дольше 5 с | Бесконечный спиннер, пульсирующий орб |
| Статичные скелетоны карточек справа | Shimmer, пульсация, скелетон текста ответа в ленте |
| Честный `progress.slow` после 10 с | Прогресс-бар с процентом |
| Бейдж на месте строки стадии, высота та же | Ответ, сдвигающий ленту при появлении бейджа |
