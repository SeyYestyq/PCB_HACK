Document 1──1 Edition            (для законов edition.status всегда current)

## 3. Файлы индекса (артефакты ингеста)
| Файл | Формат | Содержимое |
|---|---|---|
| `kb_manifest.json` | JSON | `kb_hash`, `built_at`, `parser_version`, `documents[]` (Document без `text`), `editions[]`, `relations[]`, `warnings[]` |
| `units.jsonl` | JSONL | Unit без `tokens_stem` |
| `psb_index_<kb_hash>.npz` | numpy | `emb` float32 [N×1024] L2-нормированные; `unit_ids`; BM25 статистики (`df`, `idf`, `doc_len`, `avgdl`), словарь стеммов |
| `kb_expected_manifest.json` | JSON (роль 3) | ожидаемые doc_type, номера, редакции, связи; тест сравнивает с `kb_manifest.json` |

`kb_hash = sha256(join(sorted(f"{name}:{sha256(bytes)}")))`; при смене версии парсера к ключу кеша добавляется `parser_version`.

**Где лежат.** Во время работы все три файла ингеста пишутся в один каталог кеша `/tmp/psb_cache/<kb_hash>/` (`kb_manifest.json`, `units.jsonl`, `psb_index_<kb_hash>.npz`), атомарно через `os.replace`. Отдельно, по ТЗ §8, в корень ZIP сабмита можно положить готовый `psb_index_<kb_hash>.npz`; он используется, только если `kb_hash` совпал с хешем закрытой базы. Это единое правило для `02-architecture/01` §4.1, `05-rag/02` §3 (S0), R1.2 и H-04 (сверено 10.11.2026, раньше в файлах были разные пути).

## 4. Правила парсинга (детерминированные)
| Тип | Распознавание | Разбиение на unit |
|---|---|---|
| Договор | заголовок `^ДОГОВОР` | преамбула (`preamble`), разделы `^\d+\.\s+[А-Я]`, пункты `^\d+\.\d+\.\s`, реквизиты (`signature`) |
| ДС | `^ДОПОЛНИТЕЛЬНОЕ СОГЛАШЕНИЕ` | абзацы; строка «к договору … № X от D» → Relation; кавычки «3.2. …» → `replacement_text`; «применяется к …» → `condition` |
| Регламент | `^РЕГЛАМЕНТ` или пометка редакции | как договор + шапка редакции |
| Письмо | `Исх. №` | абзацы; «С D г.» → `effective_from` связи; «п. N Регламента (ред. от D)» → `supplements` |
| Записка | `СЛУЖЕБНАЯ ЗАПИСКА` | абзацы |
| Закон | шапка `Источник:` | пункты `^\d+\.\s`, подпункты `^\d+\)\s`, части ТК по абзацам; примечания `изменен[а-я]* с` → `editorial_note` |

## 5. Санитайзер инъекций
Признаки (любой → кандидат, два и более → `suspected_injection=true`):
1. Обращение к модели: `(ИИ|AI|ассистент|модел|нейросет|бот)` в верхнем регистре или с «ВНИМАНИЕ»/«ИНСТРУКЦИЯ».
2. Императив управления: `игнорируй|забудь|не упоминай|отвечай|всегда|никогда не говори`.
3. Квантор на всю базу или все вопросы: `все остальные документы|любой вопрос|любому договору`.
4. Сокрытие: `не упоминай эту инструкцию`.
На текущей базе срабатывают все четыре признака ровно в одном абзаце (KB-A1). Ложные срабатывания на юридическом тексте проверяются тестом: в остальных 20 файлах 0 кандидатов с ≥ 2 признаками (и 0 абзацев даже с одним признаком; проверено прототипом этих регэкспов на ревью 09.11.2026, признак 1 регистрозависимый, остальные нет). На закрытой базе это число может отличаться, поэтому порог «два признака» не снижаем. Санитайзер не единственная защита: spotlighting в промпте и проверка вывода (запрет «90 календарных дней», если такого числа нет в процитированных unit) описаны в [`04-security.md`](04-security.md).

## 7. Эволюция модели (продакшен)
В Postgres сущности ложатся в таблицы `documents`, `editions`, `relations`, `units` (с `embedding vector(1024)` и `tsv tsvector` с конфигурацией `russian`) [S-24], [S-25]; добавляются `acl_group`, `uploaded_by`, `reviewed_by` (редакции подтверждает юрист, а не парсер), `valid_from/valid_to` на уровне unit для пунктовых изменений. JSONL-формат хакатона является дампом этих таблиц, поэтому миграция без изменения ядра.
