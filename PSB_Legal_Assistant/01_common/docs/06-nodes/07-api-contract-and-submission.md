## 1. Место в потоке
Единственное место, где путь сабмита и путь веба расходятся. До S17 всё общее; рендер различается потому, что потребители разные: LLM-судья читает одну строку текста, интерфейс читает структуру.

**Инварианты.**
- I-ND7-1: `submission.csv` создаётся всегда, в рабочем каталоге, UTF-8, заголовок ровно `id,answer`, все ID из `questions.csv`, без повторов, ответы непустые и ≤ 10 000 символов, стандартное CSV-экранирование [K-REG §3], [K-REG §9].
- I-ND7-2: в ZIP только корневые `.py` и `requirements.txt` с зафиксированными версиями из разрешённого списка; никаких `pip install` из кода [K-REG §4].
- I-ND7-3: ключи только из окружения, не в коде, не в файлах, не в логах [K-REG §6].
- I-ND7-4: HTTP-контракт `AnswerV2` версионирован (`schema_version`); v1-поля (`status`, `answer`, `citations[{doc_id,title,span,quote}]`, `missing`) сохраняются на переходный период, чтобы не сломать текущий UI.
- I-ND7-5: SSE является улучшением, а не зависимостью: при любой ошибке потока UI получает тот же ответ обычным POST.

## 3. To-be спецификация
### 3.1. Текст для судьи (S18)
Структура эталона [K-DEMO]: прямой ответ → значение → ссылка «(п. N)» или «Источник: договор № …, п. N» → ограничения или `missing`. Одна строка, без markdown, рекомендуемо до 150 слов [K-REG §3]. Название документа берётся из метаданных («договор аренды № А-08/2024 с ООО «Северный Склад»»), а не из имени файла. Для `abstain` и `refuse_role` текст объясняет, чего не хватает или почему вопрос вне роли, и никогда не пуст.

### 3.2. `solution.py`
1. Без аргументов = батч: `DATA_DIR` или `data`; `questions.csv`, `knowledge-base.zip`; вывод `./submission.csv`.
2. Индекс строится до первого вопроса (ND1, ND2), с кешем по `kb_hash`.
3. Пул `MAX_WORKERS` (из окружения, по умолчанию 4); общий семафор на внешние вызовы.
4. Каждый вопрос в `try/except`: любое исключение даёт L4-ответ или честный `abstain`-текст; таймаут вопроса 60 с.
5. Глобальный дедлайн 17 минут из 20 [K-REG §5]; по прогнозу включаются уровни L1-L4 (05-rag/02 §4).
6. Чекпоинты: каждые 10-20 ответов CSV переписывается целиком во временный файл и переименовывается `os.replace` (атомарно по POSIX [S-97]); модуль `csv` с `QUOTE_ALL` [S-98], как сейчас (solution.py 60), сохраняется.
7. Перед выходом валидатор: заголовок, все ID, без повторов, непустые, ≤ 10 000 символов. Если ID во входном `questions.csv` повторяется, в выход идёт одна строка на ID (ответ на первое вхождение), повторы пишутся в stderr: регламент требует, чтобы ID не повторялись, и называет повтор ошибкой формата данных [K-REG §3, §9] (RG-SUB-04, UT-CSV-03).
8. Два класса отказов разделены. **Системный** (нет `questions.csv`, нет колонок `id,question`, база не читается или пуста) проверяется до открытия выходного файла: понятное сообщение в stderr, код выхода не 0, прежний `submission.csv` не трогается (`RG-SUB-09`). As-is `load_kb` вызывается на каждом вопросе, поэтому битая база падает только на первом вопросе, прошедшем гарды, когда заголовок уже записан. **Отказ одного вопроса** изолируется по п. 4: строка получает L4 или `abstain`-текст, ID и тип исключения пишутся в stderr, в конце печатается счётчик «ответов на запасном уровне: N из M». Это та же схема, что пропуск записей с лимитом в пакетной обработке, где решение о пропуске принимает тот, кто понимает данные, а пропущенные записи логируются [S-145]. Для нас запасной ответ лучше пустой ячейки, но если на запасной уровень ушло больше половины вопросов, это почти наверняка системная ошибка: прогон помечается в логе как неуспешный, и сабмит с ним не отправляется без разбора.

### 3.3. HTTP API
`POST /api/v1/ask` → `AnswerV2` (+ v1-поля); `POST /api/v1/ask/stream` → SSE; `GET /api/v1/docs/{doc_id}` → полный текст и метаданные; `GET /api/v1/kb` → `kb_hash`, число документов, без путей; `GET /health`. Ошибки клиента: 422 с машинным кодом (`question_too_long`) и текстом для UI.

### 3.4. SSE
Поток `text/event-stream` [S-95]: события `stage` (значения только из `progress.search`, `progress.verify`, `progress.cite` в [`../04-brand/03-components-and-copy.md`](../04-brand/03-components-and-copy.md) §15), затем одно `answer` с полным `AnswerV2`, затем закрытие. Ответ целиком, без потоковой выдачи токенов: показывать можно только проверенный ответ (ND6). FastAPI отдаёт поток через `StreamingResponse` [S-102].

Важная деталь транспорта: браузерный `EventSource` открывает поток по URL и не отправляет тело запроса (WHATWG создаёт запрос из URL и флага credentials [S-95]); а вопрос до 4000 символов с историей в URL не помещается разумно. Поэтому клиент читает поток через `fetch` с `ReadableStream` и разбирает формат SSE сам; `EventSource` не используется. Второе ограничение: без HTTP/2 браузер держит не больше 6 соединений SSE на домен [S-96]; поток закрывается сразу после события `answer`.

## 4. Почему так
1. **Сабмит должен выжить при любой ошибке.** Ноль баллов у судьи означает недопуск к экспертной оценке [K-PDF «Допуск»]. Регламент сам перечисляет типовые ошибки: «Отсутствует submission.csv», «Не хватает данных», «Превышено время обработки» [K-REG §9]. Каждая закрывается конкретным механизмом §3.2.
2. **Атомарная запись и чекпоинты.** Тайм-аут платформы убивает процесс; без чекпоинта файл пуст или обрезан. `os.replace` атомарен [S-97].
3. **Ограниченные повторы с jitter.** Регламент: «добавьте ограниченное число повторных запросов с паузой; не запускайте безлимитные запросы» [K-REG §9]. Экспоненциальная пауза с jitter снижает число вызовов и время до завершения по сравнению с паузой без jitter [S-88]; неограниченные повторы являются классическим механизмом каскадного отказа [S-87].
4. **Зафиксированные версии.** pip: закрепление `==` защищает от несовместимостей новых версий [S-89]; кейс и регламент требуют фиксации [K-REG §4], [K-PDF].
5. **Контракт как схема, а не как реализация.** Роль 2 работает на фикстурах до готовности ядра; изменение контракта ломает потребителя явно, через контрактный тест. Это идея consumer-driven contracts [S-72], инструментально Pact [S-73]; для OpenAPI свойства схемы можно проверять генеративно (Schemathesis [S-92]).

## 5. Отвергнутые альтернативы
| Альтернатива | Почему нет |
|---|---|
| Go BFF перед Python-ядром | второй сервис без пользы; FastAPI уже даёт OpenAPI и threadpool для `def`-эндпоинтов [S-64]; ADR-09 |
| WebSocket вместо SSE | двусторонний канал не нужен; SSE проще проксировать |
| Потоковая выдача токенов ответа | показывает непроверенный текст; противоречит fail-closed и брендбуку (запрет посимвольной печати) |
| Ядро как пакет в `apps/answer-core` для сабмита | платформа переносит только корневые `.py` [K-REG §4] |
| Индекс в ZIP всегда | регламент разрешает, но привязывает сабмит к конкретной базе; закрытая база может отличаться, поэтому индекс в ZIP только с проверкой `kb_hash` |

## 6. На что влияет
Допуск к экспертам, «Работоспособность» 20% (одна команда `docker compose up --build`, основной сценарий), «Скорость» 15% (бюджет и параллелизм), «Интерфейс» 15% через полноту контракта. Ошибка в рендере текста для судьи обесценивает всю работу ND1-ND6.

## 7. Как проверять
| Что | Тест |
|---|---|
| ZIP в пустой папке, `DATA_DIR` с фикстурами, без аргументов → валидный CSV | `RG-SUB-01`, `RG-DEF-D2`, `RG-DEF-D3` |
| Исключение на одном вопросе → остальные ответы есть, у проблемного непустой текст | `RG-DEF-D22`, `RG-SUB-08` |
| Убийство процесса на середине → на диске валидный последний чекпоинт, прежний `submission.csv` не затёрт | `RG-SUB-05` |
| База не читается → понятная ошибка до открытия `submission.csv` | `RG-SUB-09` |
| Прогон укладывается в бюджет, понижая уровни | `RG-SUB-07` |
| 11 строк матрицы «поле API → экран» `04-brand/04`: 10 состояний `AnswerV2` по JSON Schema и конверт ошибки | `CN-RESP-01..11` |
| SSE: только `stage` из словаря, затем `answer`, затем закрытие; ответ идентичен POST | `CN-SSE-01..05` |
| 4001 символ → 422 `question_too_long` | `CN-REQ-02` |
| `docker compose up --build` на чистой машине: 3000 и 8090 отвечают | `RG-API-01` |
| В логах нет значения `LLM_API_KEY` | ТЗ F17 (grep ключа в логах = 0), SEC5; отдельного ID в каталоге нет (до v1.6 здесь ошибочно стоял `RG-API-06`, это тест эндпоинта документа) |

## 8. Режимы отказа
| FM | Симптом | Деградация |
|---|---|---|
| FM-ND7-1 | исключение в ядре на вопросе | L4 или `abstain`-текст для этого ID |
| FM-ND7-2 | приближение к 20 минутам | уровни L1-L4; финальный чекпоинт до дедлайна |
| FM-ND7-3 | поток SSE оборвался | UI повторяет запрос POST-ом (I-ND7-5) |
| FM-ND7-4 | ответ длиннее 10 000 символов | обрезка по границе предложения с пометкой |
| FM-ND7-5 | `401 token_not_found_in_db` | не повторять; лог и сообщение организаторам [K-REG §9]; CSV с честными ответами L4 |
