> Статус: RFC, версия 1.0, 9 ноября 2026. Формат каждого решения: контекст, варианты, критерии, решение, последствия, источники (все открыты при подготовке, полный реестр в [`../99-sources.md`](../99-sources.md)), условия пересмотра.
> Отношение к `DECISIONS.md` [K-INTAKE]: там зафиксировано «Python (FastAPI) + React/Vite/TS + Postgres/pgvector» и «один shared answer-core». Мы сохраняем Python/FastAPI и единое ядро, **уточняем** роль Postgres (продакшен-профиль, не контур сабмита) и **оставляем Next.js** вместо Vite, потому что он уже в репозитории и работает. Оба уточнения нужно внести в `DECISIONS.md` датой 10.11 с этой аргументацией.
> Как ревьюить новые ADR: [`../08-review/03-architecture-review.md`](../08-review/03-architecture-review.md) (v1.3).

## ADR-01. Язык и форма ядра
**Контекст.** Сабмит: только корневые `.py` и `requirements.txt` из разрешённого списка (26 пакетов, среди них numpy, httpx, openai, fastapi, rank-bm25, bm25s, scikit-learn, faiss-cpu, chromadb, rapidfuzz, python-docx, langchain, SQLAlchemy без драйвера Postgres) [K-REG §4], [K-REQ]. Стартер организаторов на Python [K-SAMPLE].
**Варианты.** (a) Python плоские модули; (b) Python-пакет с вложенными папками; (c) другой язык для веба + Python для сабмита.
**Решение.** (a). Пакетная структура на платформе ломается (дефект D3 as-is); (c) нарушает «один путь» [K-INTAKE DECISIONS].
**Последствия.** Имена модулей с префиксом `psb_` (без коллизий со стандартной библиотекой); FastAPI-сервис импортирует те же файлы; Docker-образ `answer` копирует корневые `psb_*.py`.
**Пересмотр.** Если организаторы разрешат пакеты в ZIP.

## ADR-02. Хранилище и поиск: in-memory против Postgres+pgvector, Qdrant, OpenSearch, только FTS
**Контекст.** База: 21 файл, ~270 тыс. символов, ~340-350 unit после структурного разбиения (замер прототипа: 337 unit, медиана 721 символ). Векторы 1024-мерные [S-34]: 350 × 1024 × 4 байта ≈ 1.4 МБ. Сабмит не может поднимать сервер и не имеет драйвера Postgres в списке [K-REQ].
**Критерии.** (1) работает в сабмите; (2) один ретривер в демо и сабмите; (3) качество гибрида; (4) операционная сложность; (5) путь в продакшен банка.
| Вариант | (1) | (2) | (3) | (4) | (5) | Источники |
|---|---|---|---|---|---|---|
| In-memory: numpy точный косинус + свой BM25 | да | да | гибрид RRF вручную | минимальная | через интерфейс `Retriever` | [S-31] (faiss избыточен для сотен векторов), [S-29], [S-28] |
| Postgres 16 + pgvector + FTS | нет (нет драйвера, нет сервера) | только если сабмит другой | гибрид SQL-запросом: pgvector README показывает объединение с полнотекстом, по умолчанию точный поиск, HNSW/IVFFlat как приближённые индексы | средняя | лучший: одна СУБД для метаданных, векторов, FTS, ACL, аудита | [S-24], [S-25], [S-26] |
| Qdrant | нет | нет | встроенный hybrid query с RRF/DBSF и prefetch | средняя (отдельный сервис) | хороший, но отдельный стек хранения | [S-16] |
| OpenSearch | нет | нет | hybrid search с нормализацией и комбинацией оценок в search pipeline | высокая (JVM) | хороший для больших корпусов | [S-18] |
| Только FTS (Postgres или BM25) | да (BM25) | да | без семантики: парафразы теряются (провалы прототипа на Q7, Q9, Q17 именно парафразы) | минимальная | слабый | [S-15] (гибрид + реранк лучше чистых каналов), [S-19] |
**Решение.** In-memory в обоих контурах хакатона; Postgres+pgvector+FTS как продакшен-целевое хранилище и опциональный compose-профиль `full` (уже есть [K-CODE]), не используемый в демо.
**Почему не «Postgres в демо, in-memory в сабмите».** Два ретривера дают разные top-k, значит разные ответы в демо и у судьи; на защите это видно на первом же совпадающем вопросе. Выигрыша по скорости на 350 векторах нет: точный поиск numpy занимает миллисекунды (вывод из размера матрицы; замер добавить в `docs/perf.md`).
**Сомнение, которое мы проверили.** «Эксперты оценивают архитектуру (20%), и векторная БД выглядит солиднее.» Ответ: критерий называется «архитектура и работа с документами» [K-PDF]; баллы дают структура unit, редакции и проверка, а не наличие СУБД. Продакшен-схему с Postgres показываем как сценарий внедрения (15% защиты).
**Пересмотр.** База > 50 тыс. unit или требование ACL/аудита в демо.

## ADR-03. Гибрид и способ слияния
**Контекст.** Юридические вопросы содержат точные идентификаторы (П-17/2024, п. 2.4, ИНН), где сильна лексика, и парафразы («сколько платим за склад»), где сильна семантика.
**Варианты.** (a) RRF; (b) взвешенная сумма нормализованных оценок (alpha); (c) DBSF; (d) только dense.
**Доказательства.**
- Microsoft Azure AI Search: гибрид + семантический реранк превосходит каждый канал по отдельности на их наборах [S-15].
- Elasticsearch: RRF с `rank_constant` по умолчанию 60, не требует калибровки оценок [S-17].
- Qdrant: RRF и DBSF как штатные способы слияния, prefetch по каналам [S-16].
- Weaviate: гибрид как alpha-взвешивание BM25F и вектора, плюс RRF [S-19].
- BGE-M3 model card прямо рекомендует «hybrid retrieval + re-ranking» [S-34].
**Решение.** RRF k=60 по двум спискам top-30. Alpha-взвешивание отвергнуто: шкалы BM25 и косинуса несопоставимы, калибровать на 18 демо-вопросах значит переобучиться. Первоисточник RRF (Cormack et al.) открыть не удалось (403/500), формула взята из документации Elastic и Qdrant, это отмечено в реестре.
**Пересмотр.** Если на golden RRF проигрывает alpha > 3 п.п. recall@8 при кросс-валидации по типам кейсов.

## ADR-04. Лексический канал
**Контекст.** Русская морфология требует стемминга; PyStemmer, nltk, pymorphy в разрешённом списке отсутствуют [K-REQ]; bm25s умеет стемминг только через PyStemmer [S-28].
**Варианты.** (a) rank_bm25 + свой Snowball RU; (b) bm25s без стемминга; (c) TF-IDF `char_wb` n-граммы (sklearn) [S-30]; (d) готовый стеммер, скопированный в код.
**Решение.** (a): реализация Snowball Russian по формальному описанию алгоритма [S-27] (~150 строк, детерминированно, покрывается тестами на словарных парах), BM25Okapi [S-29] или своя векторизованная версия на numpy. (c) держим как запасной канал для опечаток (кейс `ROB`), включаемый флагом.
**Детали токенайзера (важно для юр. текста):** номера документов `[А-ЯA-Z]{1,3}-\d+/\d{4}` как один токен + составные части; суммы с пробелами-разделителями тысяч склеиваются («450 000» → `450000`); даты в ISO; «п. 2.4» → токен `p2.4`; латиница/кириллица в номерах унифицируются (P-17 → П-17).
**Пересмотр.** Если организаторы добавят PyStemmer в список.

## ADR-05. Эмбеддинги
**Контекст.** Платформа предоставляет BGE-M3 через `/embeddings` [K-REG §6], [K-SAMPLE].
**Доказательства качества для русского.** ruMTEB: BGE-M3 Retrieval 74.79, лучший среди 10 моделей таблицы [S-35]; статья M3: мультиязычность 100+ языков, до 8192 токенов [S-33]; карточка: 1024 измерения [S-34].
**Ограничения.** Через прокси доступен только dense-выход; sparse и multi-vector выходы M3 [S-33] недоступны, поэтому лексика своя (ADR-04). Late chunking [S-06] невозможен без доступа к токенным эмбеддингам.
**Решение.** BGE-M3 dense для unit с контекстным префиксом «Документ: … | Раздел: … | п. N» (идея contextual retrieval [S-07], но префикс детерминированный, без LLM-вызова на unit).

## ADR-06. Реранкер
**Контекст.** Платформа указывает Qwen3-Reranker-8B [K-REG §6]; стартер по умолчанию `cohere/rerank-5-fast` [K-SAMPLE] (расхождение с регламентом: используем только значение из окружения `RERANKER_MODEL`).
**Доказательства.** Qwen3 Embedding/Reranker: instruction-aware, многоязычный [S-36]; карточка: 32k контекста, результаты MMTEB-R [S-37]; Azure: реранк поверх гибрида даёт прирост [S-15].
**Риск.** Каждый вызов реранка добавляет сетевую задержку на вопрос; на 200 вопросах в 20 минутах это заметно.
**Решение.** Включаем собственным флагом `PSB_RERANK=1`; модель берём из `RERANKER_MODEL`. Переменную стартера `RERANKER_TOP_N` как `top_n` не используем: стартер ограничивает её диапазоном 1-5 с умолчанием 2 [K-SAMPLE `solution.py`], а нам нужен top-8 для контекста (05-rag/02 S11). A/B на golden (recall@8, статус-точность) и замер p95; по умолчанию «вкл» только если прирост ≥ 2 п.п. recall@8 и p95 не выходит за бюджет. Таймаут 4 с, при таймауте пропуск (L1).

## ADR-07. Чанкинг
**Доказательства.** NitiBench: в юридическом домене section-based разбиение значимо лучше наивного [S-09]; SAT-Graph RAG: сегментация по статье/части/пункту [S-10]; LegalBench-RAG: важна точность минимального фрагмента [S-50]; Dense X: мелкие единицы извлечения полезны [S-08].
**Решение.** Unit = пункт договора/регламента, абзац письма, часть/пункт статьи закона; при генерации короткие документы компании подаются целиком (parent expansion), так как вся компания-часть базы ~16 тыс. символов. Подробности и замеры: 05-rag/01 §3.

## ADR-08. Генерация и проверка
**Контекст.** Модель DeepSeek V4.1 Flash из окружения [K-REG §6]. JSON-режим: `response_format: {"type": "json_object"}`, в промпте должно быть слово json и пример, возможен пустой `content` [S-54]; контекст 1M токенов [S-69]. В официальном API thinking включён по умолчанию и `temperature` в нём не действует [S-70]; как ведёт себя прокси платформы, неизвестно (открытый вопрос 4 ниже).
**Варианты проверки.** LLM-as-critic (Self-RAG [S-39], CoVe [S-43]), NLI [S-42], детерминированные проверки цитаты/чисел/редакции.
**Решение.** Генерация JSON с claims, каждый claim с `unit_ids` и дословной `quote`; детерминированная проверка (подстрока, числа из claim присутствуют в цитате, редакция применима к дате события) и не более одного repair-вызова. LLM-критик не используется в сабмите (время и недетерминизм), допустим как офлайн-оценщик. Обоснование: ALCE показывает, что даже сильные модели плохо цитируют без контроля [S-41]; Stanford: юридические RAG-инструменты ошибаются в 17-33% запросов, отдельный тип ошибки «misgrounded» [S-48], [S-49].

## ADR-09. HTTP-слой: FastAPI против Go BFF
**Варианты.** (a) FastAPI напрямую; (b) Go BFF (`apps/api`) → FastAPI; (c) Next.js route handlers → ядро через subprocess.
**Аргументы.** FastAPI исполняет `def`-эндпоинты в threadpool, что подходит блокирующему ядру [S-64]; уже работает в репозитории [K-CODE]; Go BFF добавляет хоп, язык и сборку без функции (авторизации в демо нет); DECISIONS откладывает Go [K-INTAKE].
**Решение.** (a). `apps/api` остаётся в профиле `legacy` до удаления.

## ADR-10. UI: Next.js 15 против Vite
**Контекст.** DECISIONS называет React/Vite, но в репозитории Next.js 15.1.0 с рабочим `LegalChat` и Dockerfile [K-CODE].
**Доказательства.** React рекомендует начинать с фреймворка, Vite упомянут как вариант для сборки своего стека [S-67]; Vite даёт быстрый dev-сервер и статическую сборку SPA [S-66]; Next.js `output: 'standalone'` даёт минимальный образ для Docker [S-65].
**Критерии.** Время до рабочего UI, риск миграции за 7 дней, размер образа, SSR не нужен.
**Решение.** Оставить Next.js 15 (App Router, клиентский компонент чата, standalone-сборка). Миграция на Vite не даёт пользователю ничего и стоит 1-2 дней роли 2. Внести уточнение в DECISIONS.
**Пересмотр.** Если сборка Next в Docker превышает 5 минут или ломается на чистой машине.

## ADR-11. Поставка
**Решение.** Корневой `compose.yaml` (канонический файл Compose [S-68], прямо назван в кейсе [K-PDF]) с сервисами `answer` и `web`; `.dockerignore` в корне; `requirements.txt` с `==`; `package-lock.json`. Ключ передаётся через `.env` (в `.gitignore`), шаблон `.env.example` без значений.

## ADR-12. Тестирование и оценка
**Доказательства.** CheckList: поведенческие тесты по типам способностей (MFT/INV/DIR) [S-47]; RAGAS и ARES: раздельные метрики faithfulness/relevance и лёгкие автоматические судьи [S-44], [S-45]; CRAG benchmark: отдельный класс false premise [S-51].
**Решение.** Юнит-тесты на чистые функции (`psb_textnorm`, `psb_structure`, `psb_verify`); golden-набор по 19 типам (ТЗ §9); суррогатный судья по методике регламента; Playwright-смоук UI.
